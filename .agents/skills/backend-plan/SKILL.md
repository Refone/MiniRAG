# 后端改动方案（调研 → 文档）

把「PRD + 前端交互 demo」翻译成**人类可直接审批**的后端改动方案。产物是设计文档，不是代码：
它要回答「改哪些文件、数据从哪来到哪去、接口长什么样、失败怎么办、怎么判定验收」。
合格的标准只有一条：**人类读完这份文档就能批准开工，不需要再翻源码**。

## 产出契约

| 项 | 约定 |
| --- | --- |
| 路径 | `docs/feat/<需求名>/后端改动方案.md`；同目录已有 `后端方案.md` / `方案设计.md` 时就地升级该文件，不新建第二份 |
| 修订产物 | `docs/feat/<需求名>/后端评审反馈-vX.md`，仅当存在人类写的 `后端评审vX.md` 时产出 |
| 规模 | 250–450 行；超过 600 行按阶段拆文件（参考 `docs/feat/任务管理升级/方案设计P1.md` / `方案设计P2.md`） |
| 必备章节 | AGENTS.md「后端改动方案.md」五章：架构调整 / 文件修改清单 / 内部重要变更 / 对外重要变更 / 验收条件 |
| 语言 | 中文、表格优先；Mermaid 只画架构与数据流，不画装饰图 |
| 归属 | AI 只写文档：`backend/`、`frontend/` 只读取证，不写代码、不建集合、不 `git add/commit` |

「信息精简，尽量突出核心改动和设计思路」是硬指标：能一行表格说清的不写三段话。

例外：演练 / 自测时若产物只能写到 gitignore 区（如 `var/tmp/`），流程照走，但交付时要注明「产物不入库」，
第 6 步第 5 条的核对方式随之改为「对照基线看改动面」。

## 按需读参考（控制上下文开销）

参考文件**不要全读**：本 SKILL 是入口，其余按任务取用，读完就动手，别反复重读。

| 任务 | 必读 | 可选 |
| --- | --- | --- |
| 首版方案 | `plan-template.md`（动笔骨架）+ `repo-map.md` 中本需求命中的「改动类型」行 | `decision-patterns.md` §3 决策族、§6 验收 |
| 评审修订（有 `后端评审vX.md`） | `decision-patterns.md` §5 + `plan-template.md` §10 | — |
| PRD 纪要追加 / 小改 | `plan-template.md` 对应章节 | — |
| 只做调研 | `repo-map.md` | — |

成本参考：全读 ≈ 10–13k token；首版典型只读入口 + 两份参考 ≈ 6–8k token。
这些约定若让 AI 从零读源码重新推导（分层归属、端点风格、计量落点），要额外读十几处代码才可能猜对，比整份 skill 更贵且更易错。

## 两种模式

1. **首版**：PRD（+ demo）→ `后端改动方案.md`，标题 `（v0）`，前言注明「状态：待评审」。
2. **修订**（先判断是哪一种，别混着做）：
   - 有 `后端评审vX.md`（含「给予评审反馈」要求）→ **先**写 `后端评审反馈-vX.md`（逐条答复 + 落定结论），**再**把结论合并进方案正文，标题版本号 +1，旧结论进「评审记录」表。
   - 只是 PRD 末尾「评审纪要」追加了要求 → 直接增量更新方案，不产出反馈文件。
   - 已动工后出现 `测试反馈.md` → 那是下一阶段文档，方案只做必要的事实校正，不写修复清单。

## 工作流

### 1. 读需求（需求侧证据）

- `PRD.md`：正文 + 文末「评审纪要 / 补充要求」。**评审纪要更晚，冲突时以它为准**。
- PRD 不存在或需求只在对话里：先让人类补 PRD，不凭对话臆测需求（SOP 的起点是文档）。
- `demo.html`（如有）：抽四类信息 —— `STATES` 列表（状态语义）、mock 常量（字段集合与量级）、交互时机（谁触发、何时刷新）、错误文案（失败语义要求）。
- 同目录其他材料：`交互评审v*.md`（交互侧硬约束，常含后端必须配合的限制）、`需求描述V*.md`、`images/`。
- 已有后端文档与仓内同类需求的方案：沿用既有措辞与已定决策，不重新发明（风格漂移是评审最常见的第一印象问题）。

产出：需求点清单 `R1..Rn`，每条标 PRD 行号与 demo 依据。

### 2. 调研代码现状（代码侧证据）

按 `references/repo-map.md` 的「改动类型 → 先读哪些文件」逐项定位，**每条结论都带 `文件:行号`**。

必答五问，答不上来就不许写方案：

1. 现有端点、挂载前缀、DTO 放在哪；
2. 目标链路当前怎么走（`api → service → graphs → common`，函数级）；
3. 数据现在存在哪、谁负责读写（Mongo / Milvus / MinIO / 进程内）；
4. 新东西应该落在哪个模块（用 tier 规则判定，不是拍脑袋）；
5. 有哪些现成能力可复用，边界在哪（能复用的写清楚，不能复用的说明为什么）。

读不到就说读不到：标 `⏳` 并写清缺什么信息，禁止「大概 / 应该 / 推测」。

调研与决策是**来回**的：写入频率、精度、失败语义这类结论往往要读到线程池、流式调用、仓储吞异常等细节才定得下来。
允许回头补 §6 决策，但交付前必须自洽——决策里写的与 §3 清单、§5 契约不能互相矛盾。

### 3. 需求 → 后端能力映射

一张表，评审靠它 30 秒判断有没有漏：

| 编号 | 需求点 | demo 依据 | 后端能力（端点/字段/事件/存储） | 现状 | 结论 |
| --- | --- | --- | --- | --- | --- |

规矩：demo 里**每个可达状态**都要有后端支撑（`loading` / `error` 也要有对应失败语义，不能只有 happy path）；PRD 有而本期不做的，写进「未覆盖」并给理由。

### 4. 抽决策点（评审真正要看的东西）

每条决策：**决策点 / 备选（≥2，含「什么都不做」）/ 建议 / 理由 / 影响面**。
按 `references/decision-patterns.md` 的决策族过一遍，防止漏掉身份、存储、实时性、错误语义这几类必答项。

- 能定 → 写「结论」+ 理由 + 被否掉的备选；
- 定不了 → 标 `⏳`，写清阻塞点和需要谁给什么答复，进「未决问题」；
- 每个 `⏳` 都必须在交付回复里再列一次，否则人类看不见该拍什么。

### 5. 写文档

骨架与各章写法见 `references/plan-template.md`，按它逐章填。三条通用要求：

- **顺序即逻辑**：前言（依据 / 状态 / 范围与基线）→ 需求映射 → 架构调整 → 文件清单 → 内部变更 → 对外变更 → 决策 → 风险 → 实施顺序 → 验收 → 评审记录；
- **改动闭环**：每个新增能力都要能顺着「端点 → service 函数 → 数据访问方法 → 存储位置」走到底，断在哪一环就补哪一环；
- **对外契约写全**：请求参数、响应示例、错误码、调用时机、失败时前端怎么表现，缺一项都算未完成。

### 6. 自检（必须真跑，不能目测）

```bash
# 1) 基线：仓库契约当前是绿的，方案不能建立在红的基线上
.venv/bin/python tools/check_layers.py && .venv/bin/python tools/check_layout.py

# 2) 引用路径是否存在：期望只输出 §3 清单里标「新增」的文件；
#    出现其它路径 = 引用写错，或清单漏登记（:行号 后缀与占位符会被跳过）
grep -oE '`(backend|frontend|docker|tools|tests|docs)/[^`]*`' docs/feat/<需求名>/后端改动方案.md \
  | tr -d '`' | grep -v '[<>*]' | sort -u \
  | while read -r p; do p=${p%%:*}; [ -e "$p" ] || echo "待新建: $p"; done

# 3) 端点清单一览（只认反引号内的整串，避免把 `backend/api/main.py` 误算成端点）
grep -oE '`/api/[a-zA-Z0-9_{}/.-]+`' docs/feat/<需求名>/后端改动方案.md | tr -d '`' | sort -u

# 4) 待拍板清单（每个 ⏳ 都要进交付回复）
grep -n '⏳' docs/feat/<需求名>/后端改动方案.md

# 5) 改动面核对：会话开始时先跑一次记作基线；交付时只允许本文档（及反馈文档）新增/修改
git status --short
```

第 3 步的清单要能与 §5.1 的端点表一一对上；对不上的（少写一个、或写了没落点）当场补。
第 5 步注意两点：基线里本来就脏的文件不算你的改动（先记基线再动手）；产物写在 gitignore 区时这里看不到产物，
改为核对「除基线脏点外没有新增改动」，并在交付里说明。

再逐条过一遍**逐项清单**：

1. 需求映射表覆盖 PRD 全部 P0 + demo 每个可达状态；未覆盖项有理由；
2. 每个端点：参数 / 响应示例 / 错误码 / 调用时机 / 数据来源 / 实现落点（service 函数 + 数据访问方法），失败路径与重复提交有语义；
3. 每个新增或修改的字段：模块、类型、默认值、示例实例、存量数据策略；
4. 文件清单与正文一致（正文提到的文件都在清单里，清单里的文件正文都交代了）；
5. 硬性规则 5–9 的勾选形式：分层与单例收口、INT64 对外 string、`/api` 前缀与错误体、单 worker 声明、存量数据策略；
6. 验收条件每条可执行、可判定（命令 / 接口返回 / 日志 / UI 现象），没有「功能正常」；
7. 有歧义处：有结论的进决策表，没结论的标 `⏳`；
8. 没有越阶段内容（不贴实现代码、不写前端组件细节、不写测试反馈）；
9. §7 有「假设」段，且假设与 §5 契约、§6 决策不冲突；
10. 横切能力（计量、限流、审计）跨 tier 时用了逆依赖——低 tier 定义协议、高 tier 实现、service 注入，而不是让 `model` / `client` 直接 import `store`。

### 7. 交付

最终回复必须包含：

- 文档路径与版本（`后端改动方案.md（v0）`）；
- **待拍板清单**：所有 `⏳`，一条一句，说明卡在哪；
- 本轮关键决策 3–5 条（一句话结论 + 理由）；
- 方案假设（PRD / demo 没写、按现有模式补的东西）与明确不做的部分；
- 下一步：评审通过（人类 commit 或答复）后才动工改代码。

只说「已生成」不算交付。

## 硬性规则

1. **只写文档**：`backend/`、`frontend/` 只读；不新增代码文件、不改 schema、不建集合、不做任何 git 写操作。
2. **证据优先**：现状结论带 `文件:行号`；拿不到证据写 `⏳`，不编造。
3. **五章必备**：架构调整 / 文件修改清单 / 内部重要变更 / 对外重要变更 / 验收条件，无变更写「无：<一句理由>」，不删章节。
4. **schema 带示例**：新增或修改的模型必须给 JSON 示例实例（与 AGENTS.md「关键 schema 提供示例数据实例」同源）。
5. **单例收口**：全局实例定义在 `common/<pkg>/`，只在 `common/<pkg>/__init__.py` 暴露；`common` 内部只允许高 tier 依赖低 tier。
6. **精度**：Milvus auto_id 是 INT64，超过 JS 安全整数，对外一律 string（既有先例 `/api/docs` 的 `doc_id`）。
7. **契约对齐既有风格**：新端点挂 `/api`；错误 `{"detail": "..."}`；分页 `offset` + `limit` + `total`。
8. **单 worker 事实**：`TASK_MANAGER` / `EVENT_BUS` 是进程内状态（TTL 兜底），方案不得默认它们跨 worker、跨重启可用；需要跨进程就显式提出存储替换。
9. **存量数据策略必须显式**：清库 / 迁移 / 容忍三选一，不允许不写。本仓通常可清库（`tools/reset_db.py`），但要在方案里写出来。
10. **精简**：不复述 PRD 原文、不贴大段现有代码（引用 `文件:行号`）、单章不超过一屏。
11. **版本与编号**：标题带 `（v0/v1…）`；决策编号 `D1/D2` 或沿用评审编号 `V1-x`；历史结论只追加进「评审记录」，不改旧编号。
12. **术语统一**：用代码里的词（`session_id`、`task_id`、`doc_id`、`file_title`、`chunk_index`），不自造同义词。

## 反模式

- 只给端点表：不写数据从哪来、写到哪、失败怎么办。
- 顺手引入新基础设施（Redis / Celery / 消息队列）却不给理由、不列备选、不说运维代价。
- 把 demo 的 mock 数值、`bsess-8f2a1c` 这类示例标识当接口契约。
- 「后续再定」「视情况处理」——要么给结论，要么标 `⏳` 并写清阻塞点。
- 改了底层返回形态（如 `minio_client.upload_file` 的返回值）却不列全部调用点，跨层影响漏项。
- 只写 happy path：404 / 413 / 500 / 超时 / 重复提交没有语义。
- 验收条件写成「功能正常」「无明显问题」。
- 方案阶段就动手：改代码、改 Milvus schema、建集合、动前端。
- 把 PRD 整段搬进方案，读者读两遍还没看到改哪个文件。
