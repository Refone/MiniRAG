# 后端改动方案 · 文档骨架与写法

骨架可直接复制到 `docs/feat/<需求名>/后端改动方案.md`，再按各章规则填。
`<...>` 是占位符，交付前必须全部替换掉——文档里残留占位符等于没写完。

## 1. 骨架

```markdown
# 后端改动方案：<需求名>（v0）

> 依据：[PRD.md](./PRD.md)（含评审纪要）· [demo.html](./demo.html)（交互契约）
> 状态：待评审 · 范围：<本期做什么> · 非目标：<明确不做什么>
> 基线：<成稿时仓库状态，如「文档管理页 P1 已落地，本文改的是 X」>

## 2. 各章规则

### 标题与前言（3 行以内）

`依据 / 状态 / 范围与基线` 三件事各一行。基线要写清「成稿时仓库处于什么状态」，
否则评审无法判断方案是对着哪个版本写的（动态仓库里这条最容易被质疑）。

### §1 需求映射

- 一章顶一万字：评审先看这张表找遗漏，再决定要不要读后面。
- 「现状」列必须来自代码调研结论（`已存在` / `部分支持（缺 X）` / `无`），不能凭感觉写。
- demo 状态与后端能力一一对齐：`loading` / `error` / `empty` 都要有对应语义。
- 未覆盖项单独一段，不混进表里。

### §2 架构调整

- 默认答案是「无。」——大多数需求只是在既有分层里加方法。**为了显得专业而画架构图是反模式。**
- 真有变化时给：新增/移位模块表（`模块 / tier / 允许依赖`）+ Mermaid 依赖图。
- 依赖方向必须能通过 `tools/check_layers.py`；同 tier 的不同子包互相 import 是硬违规。
- 新增顶层目录要同步 `README.md` 的结构树与「目录约定」表，否则 `tools/check_layout.py` 直接红。

### §3 文件修改清单

- 精确到文件，不给目录。类型只有三种：`新增` / `改` / `删`。
- 每行改动一句话说清「改了什么能力」，不写「适配」「优化」这类无法验收的词。
- 清单是**全集**：正文提到的文件必须在这里出现；这里出现过的文件，正文必须交代过。
- 不列与需求无关的文件（顺手重构、顺手格式化一律不算本方案的改动）。

### §4 内部重要变更

- 只放 AGENTS.md 点名的两类：**schema** 与**全局实例**；graphs 相关需求再加图状态一节。
- schema 一律给 JSON 示例实例：字段名、类型、量级一眼可判断（`doc_id` 用 string 的长整数字面量最能暴露精度坑）。
- 新增字段必须写默认值与存量数据策略；Milvus 集合只在不存在时创建（`prepare_docs_collection`），
  加字段意味着 **drop + 重建**，这一点要写明。
- 全局实例：定义在哪、怎么初始化、从哪个 `__init__.py` 导出、谁消费。`api` 层不得自己 `new`。
- §4.3 判定：**state 字段变了就保留本节**（节点链不变也要写一句），节点链与 state 都没变才删。
  图状态里塞业务对象（计量 sink、上下文、开关）是常见改造点；zip 扇出后 `_trace_id` 优先 `child_task_id`，别把横切信息挂在任务命名空间上。

### §5 对外重要变更

- 三个子节分别对应 AGENTS.md 的三类对外变化：HTTP 契约 / 外部服务客户端（含本地封装）/ 数据库·缓存·队列。
- **优先复用既有端点**：能靠加参数或加字段满足的就不新增端点；新增端点要给出理由（职责不同、调用时机不同、权限不同），并说明为什么不改造老的。
- 每个端点四件套不能少：**参数、响应示例、错误码、调用时机**，再加一行「实现落点」把链路接到底。
- 错误码只用仓内既有语义：`404` 不存在、`413` 超限、`500` 服务端/部分失败、`202` 受理。错误体统一 `{"detail": "..."}`。
- 改动了客户端返回形态（URL、路径、对象名）时，必须列**全部调用点**——这是跨层影响最容易漏的地方。
- 存储变更要写：对象名/集合名、字段、索引、TTL、写入时机、读写方。

### §6 关键设计决策

- 只放「有备选、需要拍板」的项，不做流水账。
- 每行必须能回答「为什么不是另一个方案」，否则这一行没有价值。
- 结论已定的写结论；评审后改主意的，追加新行并注明取代关系（`D3 取代 D1`）。

### §7 风险与未决

- 风险写真实的技术风险：精度丢失、并发写覆盖、孤儿对象、单 worker 限制、限流打满、存量数据不一致。
- **假设单列**：PRD 与 demo 没写、你按现有模式补的前提（如「上传必须带会话身份」「计数只增不减」）。
  单列的意义是评审能一眼否掉；被推翻就要改方案，藏在正文里就会被当成遗漏。
- `⏳` 未决项必须带「谁 + 给什么答复 + 不阻塞的先做什么」，不能只写「待讨论」。

### §8 实施顺序

- 只在改动跨多个子系统时写（如「先加字段 → 再写入 → 再读接口 → 最后前端」）。
- 每步要能独立验证；不能独立验证的合并成一步。

### §9 验收条件

- AI 率先提出，人类在 PRD 补充章节完善（SOP 要求）。
- 每条含：**验收项 + 判定方式**。判定方式是命令、接口返回、日志或 UI 现象，不看人。
- 覆盖五个维度：功能（happy path）/ 契约（字段与类型）/ 数据（落库与级联）/ 失败（异常路径）/ 回归（既有链路不被破坏）。
- 质量维度固定给命令：`ruff check` + `ruff format --check`、`tools/check_layout.py`、`tools/check_layers.py`、`pytest -q`。

### §10 评审记录

- 只追加不改写：`v0 首版` → `v1 采纳 V1-1..V1-4` → …
- 人类评审的结论编号（`V1-1`）与本方案的决策编号（`D1`）都在这里留痕，方便回查。

## 3. 片段范例

### 端点表（节选，来自 `docs/feat/文档管理页面/后端方案.md` §1.1）

```markdown
| 端点 | 方法 | 职责 | 数据来源 |
| --- | --- | --- | --- |
| `/api/docs` | GET | 文档列表（分页） | Milvus `minirag_docs` |
| `/api/docs/{doc_id}` | GET | 文档详情（原文 / 切块 / 特征） | Milvus `minirag_docs` + MinIO |
| `/api/files/{object_name}` | GET | 资源代理：流式返回 MinIO 对象 | MinIO |
```

### 决策记录（节选，来自同文档 §12）

```markdown
| 编号 | 事项 | 结论 |
| --- | --- | --- |
| V1-1 | MinIO 链接可达性 | 资源代理接口 + 入库写入相对代理路径；存量不考虑（清库） |
| V1-5 | 删除语义 | 不存在 404；部分失败 500 + `success:false`，不补偿 |
```

### 验收条件（节选）

```markdown
| 编号 | 验收项 | 判定方式 |
| --- | --- | --- |
| A1 | 列表按 id 降序、分页正确、total 准确 | `curl /api/docs?offset=0&limit=2`，比对 total 与条目 id |
| A2 | doc_id 无精度丢失 | 响应中 doc_id 为字符串，浏览器 `JSON.parse` 后末三位不变 |
| A3 | 删除后无残留 | Milvus `count(*)` + MinIO `mc ls` 人工核对为空 |
```
