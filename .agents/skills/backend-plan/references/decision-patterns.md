# 决策与评审（判断力部分）

方案文档的差异化价值不在「列了哪些文件」，而在**有没有把该拍板的事拍明白**。
本文件给三样东西：决策族清单（防漏）、从 demo 抽契约的方法（防误解需求）、评审协议与预答清单（防被打回）。

## 1. 什么时候必须写成决策项

命中任一条件就单独立项，不要藏在正文叙述里：

- 存在**两个以上都说得通**的做法（代理 vs 直连、内存聚合 vs 每调用写库）；
- 结论会**改变对外契约**（字段类型、状态码、路径风格、分页口径）；
- 结论会**改变数据或部署**（是否新增集合、是否需要迁移、是否要运维配合）；
- 你手上没有足够信息定，但不定就没法开工。

不满足以上条件的实现细节，写进正文即可，不要凑数。

## 2. 决策项写法

```markdown
### 决策 N：<一句话问题>

**问题**：<现状事实 + 为什么现在必须定，带 文件:行号>

**可选方案**
- **方案 A（推荐）**：<做法> —— 优点 / 缺点
- **方案 B**：<做法> —— 优点 / 缺点

**建议**：选 A，因为 <理由>；需一并明确 <遗留问题>。

**【决定】**（人类填写）

**答复与落定**：<AI 在下一轮评审反馈里回填>
```

要点：

- 「方案 A（推荐）」放在最前面，理由必须是对比性的（为什么不是 B），不是形容词。
- 每条备选都要写缺点；只列优点的方案等于没做过取舍。
- 影响面用一句话说清：改几处、动了哪些层、有没有数据兼容问题。

## 3. 决策族清单（逐项过一遍，防止漏答）

| 族 | 必答问题 | 本仓既有先例 |
| --- | --- | --- |
| 身份与标识 | 谁生成 ID、生命周期多久、浏览器会话还是聊天会话、匿名怎么算、IP 从哪取（反代后是 `X-Forwarded-For`，容器网络里是网关地址；本仓目前**没有**取 IP 的先例，要新写） | `session_id` 由前端生成并存 localStorage（`web/src/store/chatStore.ts:31`），`/api/query` 原样透传 |
| 存储选型 | 需要向量/检索 → Milvus；会话与明细 → Mongo；制品与图片 → MinIO；短生命周期实时态 → 进程内（带 TTL） | `chat_history`(Mongo)、docs/chunks(Milvus)、三制品(MinIO)、`TASK_MANAGER`(进程内) |
| 实时性 | 增量推送 / 请求返回即快照 / 前端轮询，选哪个、为什么 | `SSEEvent` 家族 + `sse_stream`；通道必须先 `create` |
| 写入时机与频率 | 每次模型调用写一次、请求结束写一次、还是内存聚合后定期落库；hot path 多一次写库能否接受 | 现状：一次查询就有 5~6 次模型调用（意图识别、HyDE、查询向量化、重排、答案生成，另有可选的融合结论），写入频率是必答项 |
| 数值精度 | 是否 INT64、是否进 JSON、前端会不会丢精度 | `/api/docs` 的 `doc_id` 一律 string |
| 错误语义 | 不存在 / 超限 / 部分失败 / 重复提交分别是什么码什么体 | 404 不存在、413 超限、500 部分失败、`{"detail": "..."}` |
| 幂等与并发 | 重复请求会不会重复计数/重复写；并发写会不会覆盖（该用 `$inc` 还是读改写） | 同名覆盖导入已有语义（`step_2_delete_old_doc`） |
| 存量数据 | 清库 / 迁移 / 容忍，三选一并写理由 | 本仓通常可清库；`tools/reset_db.py` |
| 删除与级联 | 删父要删哪些子、顺序、残留容许度、孤儿对象怎么清 | `/api/docs` 删除：MinIO 三制品 + 图片目录 + Milvus docs/chunks |
| 配置归属 | 运行时参数 / 外部服务 / 路径分别放哪；是否要同步 `.env.example` | `app_config` / `env_config` / `path_config`；`tools/make_env_example.py` |
| 安全 | 资源代理白名单与路径穿越、CORS、密钥是否入日志 | `/api/files/{object_name}` 前缀白名单 |
| 性能与限流 | 是否打满 RPM 配额、分页上限、hot path 的额外查询 | `SlidingWindowRateLimiter` + `ENV_CONFIG.dashscope.*_rpm` |
| 单 worker 约束 | 是否依赖 `TASK_MANAGER` / `EVENT_BUS` 的进程内状态；换存储的代价是否值得 | `uvicorn` 单 worker，启动时 WARN |

## 4. 从 demo 抽契约（把 UI 翻译成后端要求）

**demo 是交互契约，不是数据契约**：它告诉你「有哪些状态、什么时候刷新、失败长什么样」，
不告诉你「字段怎么存」。三条红线：

- 不把 mock 数值当真实量级（`842000` 只是排版用的样例）；
- 不把 mock 标识当业务规则（`bsess-8f2a1c` 只是演示用的字符串）；
- 不把 demo 里的字段名直接当后端字段名（demo 可能按展示需要拼装）；
- 方案的示例 JSON 里不要照抄 demo 的 mock 数值：用自洽、不同量级的示意值，且各分项与合计要对得上。

抽取方法：**demo 元素 → 它其实要求后端什么 → 落到方案哪一章**。

以 `docs/feat/Token统计/demo.html`（当前进行中的需求）为例：

| demo 里的事实 | 对后端的真实要求 | 落到哪 |
| --- | --- | --- |
| `KINDS = [llm, vlm, embedding, reranker]` | 四个分类字段 + 一个合计；分类口径与 `model/registry.py` 的四个角色对齐 | §4.1 schema、§5.3 存储 |
| `SCOPE_LABEL = {total, query, upload}` | 统计维度不止一个总数：同一份额度要能按「查询 / 上传」拆分，说明**来源维度必须入库**，否则事后无法拆 | §5.3 存储、§6 决策（是否存明细） |
| `STATES` 含 `loading` / `error` | 读取接口要有明确的失败语义与重试口径（谁重试、几次、失败是否阻塞聊天） | §5.1 错误、§9 验收 |
| `empty` / `large` 状态 | 空态=0 值可用（不能 404）；大数值=后端不许截断/取整 | §5.1 契约、§9 验收 |
| `live`：NavBar 数字随阶段跳变 | 需要「查询/上传进行中多次读取最新累计值」——决定是轮询还是 SSE 增量 | §6 决策（实时性） |
| `BROWSER_SESSION = "bsess-..."` | 统计身份是**浏览器会话**而非聊天会话，且删聊天记录不清统计（PRD 补充说明亦如此） | §6 决策（身份）、§5.3 |
| 上传也会累加（`UPLOAD_BASE`） | 导入链路的 4 个角色调用点都要计量，包括 VLM 图片识别 | §4.3 图节点、§3 文件清单 |

反过来说：demo 里**没有**的东西（并发、清空统计、跨设备、历史趋势）要在方案的「未覆盖 / 非目标」里点名，
避免评审以为你要做。

## 5. 评审反馈协议

人类评审后可能新增 `后端评审vX.md`（意见或决策项）。此时的动作顺序固定：

1. **先答复，再改正文**（不要静默重写方案，那会让评审看不到你怎么理解他的意见）；
2. 产出 `后端评审反馈-vX.md`，逐条三段式：**问题复述 → 答复 / 方案 → 落定结论**；
3. 结论合并回 `后端改动方案.md` 正文，决策记录表追加 `V<x>-<n>` 行，标题版本 +1；
4. 反馈文档保留，头部标注「✅ 已全部落定」，供日后回溯。

反馈文档骨架（与 `docs/feat/文档管理页面/后端评审反馈-v0.md` 一致）：

```markdown
# 后端评审 VX 反馈（待拍板决策项）

> 本文列出尚需拍板的问题；每项含 问题背景 / 可选方案 / 建议。
> 已确定的内容见 [后端改动方案.md](./后端改动方案.md)。

## 决策 1：<最优先的那条>

### 问题
### 可选方案
### 建议
### 【决定】（人类填写）
### 答复与落定（AI 回填）
```

判断标准：如果评审意见只是「这里写清楚点」，直接改正文并在评审记录留一行即可，不必写反馈文档。

## 6. 验收条件写法

验收条件由 AI 先提，人类在 PRD 补充章节完善。每条 = **验收项 + 判定方式**，
判定方式必须是命令、接口返回、日志或 UI 现象，不能是「感觉对」。

| 维度 | 该覆盖什么 | 坏例 → 好例 |
| --- | --- | --- |
| 功能 | happy path 的完整闭环 | 「统计正常」→「查询一次后四类用量与合计按 `llm+vlm+embedding+reranker` 相等，且与模型返回 usage 之和一致」 |
| 契约 | 字段名、类型、空值、精度、分页 | 「返回正确」→「`session_id` 原样回显；计数为整数；无数据时返回 0 值对象而非 404」 |
| 数据 | 落库位置、级联、残留 | 「数据写进去了」→「Mongo `token_usage` 每 session 一条；删除聊天记录后该条仍在」 |
| 失败 | 不存在 / 超时 / 部分失败 / 重复提交 | 「异常有处理」→「Mongo 不可用时接口返回 503 且日志有 error；重复点击不会双计数」 |
| 回归 | 既有链路不被破坏 | 「其他功能正常」→「`/api/query`、`/api/upload/sse`、`/api/docs` 全链路复跑通过」 |
| 质量 | 固定四件套 | `ruff check . && ruff format --check .`、`tools/check_layout.py`、`tools/check_layers.py`、`pytest -q` |

## 7. 预答清单（写完方案先自问，多数评审意见都落在这里）

1. 这个地址/路径在 dev 与 prod（nginx 反代、容器网络）下都成立吗？
2. 有没有 ID 会在 JSON 里丢精度？
3. 存量数据怎么办——清库、迁移还是容忍？
4. 失败一半怎么办——补偿、忽略，还是返回部分成功？
5. 多 worker 或服务重启后会怎样？方案是否默认了进程内状态？
6. 端点前缀与 `web/nginx.conf`、docker healthcheck 对得上吗？
7. 谁在什么时候调用？失败后前端看到什么？
8. 新增配置项谁来配？`.env.example` 同步了吗？
9. 会不会留下孤儿数据/对象（MinIO 目录、Milvus 行、Mongo 记录）？
10. 这次改动的回归面在哪——哪几条既有链路必须复跑？
