# 导入任务分叉 · 后端改动方案（ZIP → 每篇 md 独立任务卡）

> **状态**：已实现（2026-10-26；改动待提交）
> **需求**：任务管理升级 · ZIP 上传后的任务卡片显示问题
> **用途**：作为 AI 编码实现锚点；视觉与交互以 [`task-fork.html`](task-fork.html) 为准。
> **基线**：设计基于 `0ad2616`，实现基于 `8862aaf`（P2 暂缓）；相关现状见 `src/utils/task_utils.py`、`src/utils/node_utils.py`、`src/processor/import_processor/**`。
> **范围**：后端 `src/**` 为主；前端消费契约同步说明（视觉原型已给出）。
> **不做**：P2 任务中止、节点业务摘要（另见 [`SSE节点摘要推送设计.md`](SSE节点摘要推送设计.md)）、任务历史 / 刷新恢复、每篇 md 独立 SSE 连接。

**一句话方案**：在「解压 + md 校验完成」与「`Send` 扇出」之间插入一个 `node_md_fork` 节点，为每篇 md 生成 `child_task_id` 并通过新的 `fork` SSE 事件下发；`trace_node` 按 child 命名空间记录进度，子任务进度走新增的 `child-progress` 事件；父任务继续使用原 `task_id`、原终态语义，前端按 fork 列表渲染独立卡片。

## 0. 结论：需要后端改动

- **必须改后端**：现有 `progress` 快照只有节点中文名，没有分支身份；前端无法从 N 个同名节点还原「哪篇 md」。仅做前端只能靠猜节点名 / 日志，不可靠。
- **改动范围可控**：新增 1 个图节点（`node_md_fork`）+ 1 个分支包装节点 + 2 个 SSE 事件（`fork` / `child-progress`）；`task_utils` / `node_utils` 做命名空间与失败记录扩展；业务节点（图片识别、切分、嵌入）零改动。
- **协议兼容**：`POST /api/upload`、`GET /api/upload/sse/{task_id}`、`__close__`、父任务 `progress` 与终态语义不变；旧前端会忽略新增事件。
- **前端仍需配套**：新增 `fork` / `child-progress` 消费与子卡渲染（视觉见 [`task-fork.html`](task-fork.html)），但不新增接口，不重建上传链路。

**落地记录（实现后补）**

- 后端：`task_utils`（child 注册表 / 锁 / failed_list / 兄弟冻结）、`node_utils`（child trace + 失败不记 done）、`node_md_fork.py`、`main_graph`（包装节点 + fork 边）、`import_service`（父级 error 快照）。
- 前端：`docsStore`（fork / child-progress / 终态冻结）、`ImportChildItem`、`ImportTaskItem` 分叉树、`StatusLog` 支持非受控 details、docs.css 子卡与聚合条。
- 与设计稿的差异（均已有意为之）：
  1. `ImportFile` 额外保存父级 `failed[]`，父任务失败节点直接渲染为红色，不再用「最后一条 done」冒充失败节点；
  2. 父卡日志在 fork 时自动收起一次、完成时自动收起一次；子卡日志完全非受控，状态迁移不改 `details.open`（对应 v2 评审反馈）；
  3. 导入 SSE 收到服务端 `event: error` 后等待 `__close__` 正常关流，查询流仍维持立即关闭；
  4. `trace_node` 失败节点不再进入 done_list，只进入 failed_list。
- 已验证：真实 ZIP 解析 + 假 tail 的同步/异步 service 事件流；`npm run build`；mock SSE 下的成功 / 单篇失败卡片渲染与冻结。

## 1. 问题与证据

### 1.1 用户可见现象

上传一个含 N 篇 md 的 ZIP，左侧导入区只有**一张**压缩包任务卡，且进度会「串台」：

1. 某篇 md 的 tail 节点完成后，卡片立刻把该节点标成「已完成」，但其它 md 可能还没开始这一节点。
2. 同一个节点可能**同时出现在已完成和进行中**：分支 A 的 `add_done_node` 把它从 running 移除，分支 B 的 `add_running_node` 又把它加回 running，而 done 里已经存在同名节点。
3. 卡片无法表达「4 篇 md 中哪几篇完成、当前哪篇在跑、哪篇失败」；失败时只有整体「失败」，没有 md / 节点归因。
4. 父任务卡片的步骤列表实际上混合了 N 个并发分支的节点，节点数量不代表实际工作量，用户无法据此判断进度。

期望效果（见 `task-fork.html`）：

```text
压缩包任务卡（父）
  识别文档类别 ✓
  处理 Markdown 压缩包 ✓
  已分叉 4 个 md 任务            2 / 4 完成
  ├─ LangGraph 基础.md         已完成
  ├─ LangGraph 状态与节点.md    处理中 · 文档切分
  ├─ LangGraph 持久化与记忆.md  处理中 · 文档嵌入入库
  └─ LangGraph 人机协同.md      等待中
```

### 1.2 根因链（代码定位）

| 步骤 | 现状 | 位置 |
| --- | --- | --- |
| ① 一次上传一个 `task_id`、一条 SSE 队列 | `POST /api/upload` 生成 `uuid4().hex`，`sse_create_queue(task_id)` | `src/api/main.py:73-101` |
| ② 解压后拿到全部 md 路径 | `node_process_md_zip` 写入 `markdown_file_paths` | `nodes/node_process_md_zip.py:337-361` |
| ③ 每个 md 通过 `Send` 扇出 | `zip_fanout_router` 用 `create_state(task_id=父 task_id, file_title=md stem, ...)` | `processor/import_processor/main_graph.py:71-96` |
| ④ 分支节点用同一个 task_id 追踪 | `_task_trace` 取 `state["task_id"]`；分支 state 没有其它进度标识 | `utils/node_utils.py:86-108` |
| ⑤ 进度列表按「任务 + 节点名」去重 | `add_running_node` / `add_done_node` 在同一个 `_tasks_*[task_id]` 上操作 | `utils/task_utils.py:56-89` |
| ⑥ 进度快照没有分支身份 | `task_push_sse` 只发 `{status, done_list, running_list}` | `utils/task_utils.py:139-149` |
| ⑦ 父任务只在全图结束后置终态 | `arun_import` 在 `ainvoke` 返回后 `set_task_status(COMPLETE)` | `src/service/import_service.py:27-41` |

因此问题不是「前端渲染得不好」，而是**后端在扇出后丢失了分支身份**。前端无论怎么解析现有 `progress`，都无法还原「这个节点属于哪篇 md」。

### 1.3 为什么不能只改前端

- `progress` 载荷只有节点中文名，没有任何 md 标识；N 个分支的节点名完全相同。
- 前端解压 ZIP 只能得到文件列表，无法复用后端的图片校验、macOS 垃圾清理、路径越界校验、重名检测，也无法知道「后端实际接受了哪些 md」。
- 每个 md 单独建 SSE 连接需要 N 条连接、N 个队列与对应的重连 / 清理逻辑，复杂度远高于在现有单流里加子任务事件。
- 前端解析 loguru 日志不是数据源（多 worker / 日志落盘时不可靠）。

## 2. 目标与非目标

### 2.1 目标

1. **fork 时机明确**：只有在解压、清理、路径安全校验、md 去重全部通过、且尚未开始任何 tail 节点时，才 fork。
2. **一 md 一卡**：每篇 md 有独立的 `child_task_id`、独立状态、独立 done/running/failed 列表、独立耗时。
3. **父卡瘦身**：父卡只保留压缩包级步骤（识别文档类别、处理 Markdown 压缩包）与聚合进度，不再混入子分支节点。
4. **失败可归因**：失败落到具体 md 与具体节点；父任务失败，未完成的兄弟任务在 UI 上冻结为「未完成」。
5. **协议向后兼容**：不改 `POST /api/upload` 的请求/响应，不改 `__close__` 语义，不新增独立端点。
6. **业务零改动**：Milvus 行、MinIO 对象路径、`task_id` 归属、文档切分/嵌入逻辑均不变。

### 2.2 非目标

- P2 的中止 / 回退（`aborted`、取消检查点、写区保护）——本方案只预留终态抑制口，不实现取消。
- 节点业务摘要、耗时、序号（`nodes[]` 扩展）——见 `SSE节点摘要推送设计.md`；该扩展落地时需要同时覆盖父 `progress` 与子 `child-progress` 两种事件。
- 任务历史、刷新后恢复卡片、跨会话持久化。
- PDF / 独文件 md 的卡片形态调整；它们继续使用现有单卡片。
- 为每篇 md 建立独立 SSE 连接或独立 API 端点。
- 大规模 md（数百篇）的虚拟滚动、分页与文件系统压力优化。

## 3. 核心设计

### 3.1 fork 时机：`node_md_fork`

在父图中插入一个只负责「物化子任务 + 下发 fork 事件」的节点：

```text
修改前：
  node_entry ──(type router)──> node_process_md_zip ──(zip_fanout_router)──> Send × N
                                                                              └─> node_md_tail (子图)

修改后：
  node_entry ──(type router)──> node_process_md_zip ──> node_md_fork ──(zip_fanout_router)──> Send × N
                                                                                              └─> node_md_tail_branch (包装节点 → 子图)
```

**为什么放在这里**：

- `node_process_md_zip` 返回时，`_find_md_files` 已完成递归扫描与排序，`_normalize_single_md`、`_check_unique_stems`、图片完整性校验与冗余清理都已完成；此时 md 列表才是最终事实。
- `trace_node` 在函数成功返回后立刻把「处理 Markdown 压缩包」记为 done；因此父卡先看到解压完成，再看到 fork，语义正确。
- `node_md_fork` 是独立图节点，在图结构里就能看出「分叉」这一步；不要把副作用塞进 `zip_fanout_router`（路由函数应保持纯）。
- fork 事件入队发生在任何 `Send` 分支启动之前；`queue.Queue` 的 FIFO 保证前端一定先收到 fork，再收到子任务 `child-progress`。

**必须保持的不变量**：

| 情况 | 行为 |
| --- | --- |
| ZIP 内 0 个 md | `node_process_md_zip` 抛错 → 不会执行 fork，父任务按现状失败 |
| ZIP 内有同名 md（stem 重复） | `_check_unique_stems` 在 fork 前抛错 → 不会 fork |
| ZIP 路径越界（zip-slip） | 解压校验阶段抛错 → 不会 fork |
| ZIP 内 1 个 md | 仍然 fork 1 个子任务（统一路径，不做特例） |
| 图片缺失 / 图片下载失败 | 在 tail 分支的 `node_md_img` 内失败 → 该 child 失败，父任务失败 |
| fork 事件推送失败（SSE 队列已移除） | 不阻断图执行；子任务仍按 child_id 记录，只是前端收不到卡片（见 §6） |

### 3.2 身份模型

| 概念 | 字段 | 示例 | 用途 |
| --- | --- | --- | --- |
| 父任务 | `task_id` | `6f2c9a...` | 上传受理、SSE 队列 key、Milvus `task_id`、MinIO 日志、清场 |
| 子任务 | `child_task_id` | `6f2c9a...:md:2` | 进度命名空间（done/running/failed/status） |
| 子任务元数据 | `title` / `path` / `index` | `LangGraph 基础` / `01-基础/LangGraph 基础.md` / `0` | 前端卡片标题、tooltip、稳定排序 |

> 命名约定：Python state / task_utils 里用 `child_task_id`；SSE JSON 里用更短的 `child_id`，两者值相同。前端类型统一用 `child_id`，不要混用。

**关键决策：分支 state 里的 `task_id` 保持不变，仍是父任务 id。**

- `node_document_embedding` 用 `state["task_id"]` 写 Milvus `minirag_docs.task_id`，`node_md_img` 等日志也带它；改写会让「同一次上传」的溯源、删除、清场语义发生变化。
- 进度身份另开 `child_task_id`，只影响 `task_utils`，不触碰业务字段。
- `child_task_id` 格式 `f"{parent_task_id}:md:{index}"`：可读、确定、天然按父任务隔离；前端把它当**不透明字符串**，不要解析。
- `index` 来自 `_find_md_files` 的排序结果（按相对路径），保证 fork 列表顺序稳定，不会因并发完成顺序而重排卡片。

`ImportGraphState` 增加两个字段：

```python
class MdChild(TypedDict):
    child_task_id: str
    title: str          # md 文件名（不含后缀）；唯一（已由 _check_unique_stems 保证）
    path: str           # 相对解压根目录的 POSIX 路径，仅用于展示
    markdown_file_path: str  # 绝对路径，仅后端使用，不下发 SSE
    index: int


class ImportGraphState(TypedDict):
    # ...既有字段...
    child_task_id: str          # 父任务 / PDF / 独文件 md 为 ""；zip 分支为 child id
    md_children: list[MdChild]  # 由 node_md_fork 产出；父任务保留完整列表
```

> **实现注意**：LangGraph 的子图 / `Send` 只会透传 state schema 中声明的字段。任何子任务需要的字段（`child_task_id`、`file_title` 等）**必须**出现在 `ImportGraphState` 中，否则会在进入子图时被丢掉。本地已用最小图验证过：未声明的 key 会被子图 input schema 丢弃；声明后可正常透传。

### 3.3 SSE 协议扩展

新增两个事件类型（`fork`、`child-progress`），并给现有 `progress` / `child-progress` 增加可选字段。**不新增端点，也不改 `__close__`。**

```text
ready            连接建立（不变）
progress         父任务进度快照（可选 failed_list / error）
fork             ZIP 解析完成，下发子任务清单（新增）
child-progress   子任务进度快照（必带 child_id；可选 failed_list / error）（新增）
delta            查询流式增量（不变）
final            查询最终答案（不变）
error            任务级错误（不变；子任务失败时仍由父任务发 error）
__close__        关流（不变）
```

#### 3.3.1 `fork` 事件

```http
event: fork
data: {
  "parent_task_id": "6f2c9a7b...",
  "total": 4,
  "children": [
    {
      "child_id": "6f2c9a7b...:md:0",
      "title": "LangGraph 基础",
      "path": "01-基础/LangGraph 基础.md",
      "index": 0
    },
    {
      "child_id": "6f2c9a7b...:md:1",
      "title": "LangGraph 状态与节点",
      "path": "02-进阶/LangGraph 状态与节点.md",
      "index": 1
    }
  ]
}
```

| 字段 | 必有 | 说明 |
| --- | --- | --- |
| `parent_task_id` | 是 | 冗余字段，便于前端校验事件归属 |
| `total` | 是 | `children.length` 的冗余校验 |
| `children[].child_id` | 是 | 子任务进度 key，前端不解析 |
| `children[].title` | 是 | md stem，用于卡片标题 |
| `children[].path` | 是 | 相对路径，用于 tooltip / 同名消歧；**不返回绝对路径** |
| `children[].index` | 是 | 0-based，稳定排序；前端按数组顺序渲染，不按事件到达顺序 |

- 不在 fork 里下发初始 `status`：前端统一初始化为 `pending`。fork 一定先于任何 `child-progress`，顺序有保证。
- `title` 是去掉后缀的 stem（业务里就是 `file_title`）；卡片若需要展示 `.md` 后缀，前端可用 `path` 的 basename，或按 `path` 后缀拼接，不要修改后端树。
- fork 只在 ZIP 链路出现；PDF / 独文件 md 不发送。

#### 3.3.2 子任务 `child-progress` 事件

```http
event: child-progress
data: {
  "child_id": "6f2c9a7b...:md:1",
  "status": "processing",
  "done_list": ["Markdown 图片识别"],
  "running_list": ["文档切分"]
}
```

失败时：

```http
event: child-progress
data: {
  "child_id": "6f2c9a7b...:md:2",
  "status": "failed",
  "done_list": ["Markdown 图片识别", "文档切分"],
  "running_list": [],
  "failed_list": ["文档嵌入入库"],
  "error": "embedding 请求超时"
}
```

- `status` 复用现有 `TaskStatus` 值：`pending / processing / complete / failed`，**不新增状态值**。
- `done_list` / `running_list` 是**该子任务自己的**节点列表，与父任务彻底隔离。
- `failed_list` / `error` 为可选；`failed_list` 只在失败时出现，`error` 为原始异常文本（前端可截断展示，不参与业务判断）。
- 父任务继续使用 `progress` 且**不带** `child_id`；子任务进度使用独立的 `child-progress` 事件。这样旧前端即使不升级，也不会把子任务进度误当成父任务进度消费（它只会忽略未知事件）。
- `failed_list` / `error` 为空时省略。
- 事件顺序：`fork` → 各 child 的 `child-progress`（并发，互不保证先后）→ 各 child 的终态 `child-progress` → 父任务 `progress(complete)` → `__close__`。
- **单条 SSE 流**最多多传 N × 若干快照；每篇 md 的节点数固定为 3（tail），事件量可控。

#### 3.3.3 兼容性

| 组合 | 行为 |
| --- | --- |
| 新后端 + 新前端 | 按本文渲染父卡 + 子卡 |
| 新后端 + 旧前端 | 旧前端忽略未知的 `fork` 与 `child-progress`；父卡只显示压缩包级步骤，上传完成 / 队列刷新仍正常，不会出现子进度覆盖父卡的问题。**建议前后端同版发布**；灰度时需接受 tail 进度暂时不可见 |
| 旧后端 + 新前端 | 没有 `fork` / `child-progress`，新前端回退为现有「父任务进度列表」渲染，行为与今天一致 |
| 任何前端 + 断线重连 | 不重放事件；刷新后任务卡丢失（现状），不属本方案范围 |

### 3.4 子任务状态机

```text
                 first add_running_node
  pending ──────────────────────────────> processing
                                              │
                         md_tail_processor.invoke 返回
                                              ▼
                                          complete
                                              │
                         任一节点抛异常 / 子图异常
                                              ▼
                                           failed
```

- `pending`：fork 时由 `fork_task` 初始化，尚无节点运行。
- `processing`：第一次 `add_running_node(child_id, ...)` 自动从 `pending` 迁移。
- `complete`：**只在包装节点 `node_md_tail_branch` 调用的 `md_tail_processor.invoke` 正常返回后**设置；不能用「running 为空」推断（`node_md_img` 完成到 `node_document_split` 开始之间存在空窗）。
- `failed`：包装节点捕获异常后设置；`failed_list` 由 `trace_node` 记录具体失败节点，`error` 保存异常文本。
- 父任务状态保持既有语义：整体 `processing → complete / failed`。父失败时，未完成的兄弟 child 不伪造终态；前端派生「未完成」展示，后端在父终态后丢弃迟到的 child 事件。

**失败传播边界**：

- 单个 md 的 tail 失败 → 该 child 先发 `failed`（含 `failed_list`）→ 异常向上冒泡 → `arun_import` 捕获 → 父 `failed` snapshot + `error` + `__close__`。
- LangGraph 的并行分支不会因为一个分支失败而立刻杀掉其它线程（见 `方案设计P2.md` §2.2）；其它分支可能继续运行几秒。这些迟到的 child 事件在父任务已终态后会被 `task_push_sse` 丢弃，前端也不会收到（SSE 已关流）。
- 本方案**不改变**已有的「部分写入已发生」事实，也不做回退；回退属于 P2。

### 3.5 父任务语义与聚合

- **父卡**只展示压缩包级节点：`识别文档类别`、`处理 Markdown 压缩包`。父 `done_list` / `running_list` 不再包含 tail 节点。
- **聚合进度由前端根据 children 状态计算**（已 fork 数量、完成 / 处理中 / 等待 / 失败 / 未完成），后端不多发聚合字段：避免两份事实不一致，也避免每次 child 进度都重发全量 children。
- **父终态**：`arun_import` 在全图结束后置 `complete`；正常结束时所有 child 已经 `complete`（包装节点在返回前完成设置）。若出现 child 未终态而父已 complete，属于协议违例，前端记录并冻结展示；后端可在验收阶段加一条 WARN 日志。
- **父卡与子卡的关系**：父卡常驻，子卡跟随 fork 出现；父卡不因单个 child 完成而改变状态，只有父终态才改变徽标。

### 4.2 `task_utils.py`

新增内部结构（进程内，仍需遵守现有单 worker 约束）：

```python
import threading
from utils.sse_utils import SSEEvent, sse_push
from utils.logging_utils import logger

_lock = threading.RLock()
_child_parent: Dict[str, str] = {}              # child_task_id -> parent task_id
_tasks_failed_nodes: Dict[str, List[str]] = defaultdict(list)
_tasks_error: Dict[str, str] = {}

_TERMINAL = frozenset(
    {TaskStatus.COMPLETE.value, TaskStatus.FAILED.value}
    # P2: | {TaskStatus.CANCELLED.value}
)


def _is_terminal(task_id: str) -> bool:
    return _tasks_status.get(task_id) in _TERMINAL
```

核心函数（示意，保留现有风格）：

```python
def fork_task(parent_task_id: str, children: list[dict]) -> None:
    """注册子任务并下发 fork 事件；仅推送失败不阻断图执行。"""
    with _lock:
        for child in children:
            cid = child["child_task_id"]
            _child_parent[cid] = parent_task_id
            _tasks_status.setdefault(cid, TaskStatus.PENDING.value)
            _tasks_running_nodes.setdefault(cid, [])
            _tasks_done_nodes.setdefault(cid, [])
            _tasks_failed_nodes.setdefault(cid, [])
        payload = {
            "parent_task_id": parent_task_id,
            "total": len(children),
            "children": [
                {
                    "child_id": c["child_task_id"],
                    "title": c["title"],
                    "path": c.get("path", ""),
                    "index": c["index"],
                }
                for c in children
            ],
        }
    try:
        sse_push(sse_id=parent_task_id, event=SSEEvent.FORK, data=payload)
    except Exception:
        logger.warning("fork 事件推送失败: task_id={}", parent_task_id, exc_info=True)


def complete_child(child_id: str) -> None:
    with _lock:
        if _tasks_status.get(child_id) in _TERMINAL:
            return
        _tasks_status[child_id] = TaskStatus.COMPLETE.value
        _tasks_running_nodes.get(child_id, []).clear()
    task_push_sse(child_id)


def fail_child(child_id: str, error: str = "") -> None:
    with _lock:
        if _tasks_status.get(child_id) in _TERMINAL:
            return
        _tasks_status[child_id] = TaskStatus.FAILED.value
        _tasks_running_nodes.get(child_id, []).clear()
        if error:
            # 保留 trace_node 记录的最深节点异常，避免被外层包装异常覆盖
            _tasks_error.setdefault(child_id, error)
    task_push_sse(child_id)


def get_task_failed_nodes(task_id: str) -> List[str]:
    """读取失败节点列表的副本（新增，供快照使用）。"""
    return list(_tasks_failed_nodes.get(task_id, []))


def add_failed_node(task_id: str, node_name: str, error: str = "") -> None:
    """记录失败节点；不主动改状态，由 wrapper / service 统一收口。"""
    with _lock:
        if node_name not in _tasks_failed_nodes[task_id]:
            _tasks_failed_nodes[task_id].append(node_name)
        running = _tasks_running_nodes.get(task_id)
        if running and node_name in running:
            running.remove(node_name)
        if error:
            _tasks_error[task_id] = error


def task_push_sse(task_id: str) -> None:
    """快照推送：父任务走 progress；child 走父队列的 child-progress。"""
    with _lock:
        parent = _child_parent.get(task_id)
        if parent and _is_terminal(parent):
            return  # 父任务已终态，迟到的子任务进度不再推送
        payload = {
            "status": get_task_status(task_id),
            "done_list": get_task_done_nodes(task_id),
            "running_list": get_task_running_nodes(task_id),
        }
        if _tasks_failed_nodes.get(task_id):
            payload["failed_list"] = get_task_failed_nodes(task_id)
        if _tasks_error.get(task_id):
            payload["error"] = _tasks_error[task_id]
        if parent:
            payload["child_id"] = task_id
        sse_id = parent or task_id
        event = SSEEvent.CHILD_PROGRESS if parent else SSEEvent.PROGRESS
    sse_push(sse_id=sse_id, event=event, data=payload)
```

`add_running_node` / `add_done_node` 需要在锁内执行「查重 + append/remove」，并在 child 第一次 running 时把 `pending` 改成 `processing`；`clear_task(task_id)` 扩展为级联清理 `child_task_id`、`_child_parent` 与 `failed/error` 条目（幂等）。`set_task_status` / `get_task_status` 也建议纳入同一把锁，保证父终态检查读到一致值。

> **为什么必须加锁**：`Send` 分支在 LangGraph 的线程池里并发执行；当前「先判断 `node not in list` 再 append」的写法存在竞态，多分支下可能出现重复行。加锁后 `fork` / 进度 / 终态更新串行化，`sse_push` 放在锁外避免持锁调用队列。

### 4.3 `node_utils.py`

```python
def _trace_id(state) -> str:
    return (
        state.get("child_task_id")
        or state.get("task_id")
        or state.get("session_id")
        or "-"
    )


def wrapper(state, *args, **kwargs):
    trace_id = _trace_id(state)
    add_running_node(trace_id, node_name, need_push=need_push)
    try:
        result = func(state, *args, **kwargs)
    except Exception as e:
        add_failed_node(trace_id, node_name, str(e))
        raise
    add_done_node(trace_id, node_name, need_push=need_push)
    return result
```

### 4.4 新增 `node_md_fork.py`

```python
from pathlib import Path

from common.config.env_config import ENV_CONFIG
from processor.import_processor.state import ImportGraphState, MdChild
from utils import task_utils
from utils.logging_utils import logger
from utils.node_utils import trace_node


@trace_node(desc="拆分 md 子任务", task_trace=False)
def node_md_fork(state: ImportGraphState) -> ImportGraphState:
    """在扇出前物化 md 子任务，并下发 fork SSE 事件。

    - 只读 markdown_file_paths；不改变业务字段。
    - fork 推送失败不阻断图执行（SSE 队列可能已被客户端断开清理）。
    - 幂等：节点被重试时不重复注册 / 重复下发。
    """
    if state.get("md_children"):
        return state

    task_id = state.get("task_id", "")
    md_dir = (
        Path(ENV_CONFIG.output_dir.import_tmp_dir) / state.get("file_title", "")
    ).resolve()

    children: list[MdChild] = []
    for index, md_path_str in enumerate(state.get("markdown_file_paths", [])):
        md_path = Path(md_path_str)
        try:
            relative_path = md_path.resolve().relative_to(md_dir).as_posix()
        except ValueError:
            relative_path = md_path.name
        children.append(
            {
                "child_task_id": f"{task_id}:md:{index}",
                "title": md_path.stem,
                "path": relative_path,
                "markdown_file_path": str(md_path),
                "index": index,
            }
        )

    if children:
        task_utils.fork_task(task_id, children)
        logger.info("md 任务分叉: task_id={}, count={}", task_id, len(children))

    # 放在 fork_task 之后：注册/推送成功才落 state，节点重试时不会跳过 fork
    state["md_children"] = children
    return state
```

- `task_trace=False`：不要让「拆分 md 子任务」进入父任务的 done_list；它只是编排动作。
- 若 `markdown_file_paths` 为空，`node_process_md_zip` 已经抛错，正常不会到这里；这里仍然做防御，`children` 为空则不注册。
- `title` 用 stem（与现有 `file_title` 口径一致）；`path` 仅用于展示。

### 5.3 `docsStore`

| 事件 | 处理 |
| --- | --- |
| `onFork` | 按 `children` 数组顺序创建子任务，全部 `pending`；`forked = true`；不刷新文档列表 |
| `onChildProgress` | 只更新对应 child：`done/running/failed/status`；`complete → completed`、`failed → error`；不触碰父任务 done/running |
| `onProgress` | 维持现有逻辑：更新父任务状态与父级步骤；`complete` 时刷新列表（沿用 `refreshedTasks`，按父 `task_id` 去重） |
| `onError` / 断连 | 父任务 `error`；未终态 child 置 `interrupted`；已失败 child 保留 `error`；停止所有计时 |
| `onServerClose` | 只关闭连接；若父任务仍未终态，按断连处理；不重复刷新 |
| 父任务 `complete` 但存在未终态 child | 记录 console.warn（协议违例），将未终态 child 冻结为 `interrupted`，不伪造完成 |

- **不要按事件到达顺序重排子卡**：fork 数组顺序即 UI 顺序。
- **不要每个 child 完成都刷新文档列表**：只在父 `complete` 刷新一次。
- **不要持久化子任务**：刷新丢卡是现状，本方案不改。
- 父任务卡渲染：父级步骤 + 聚合计数 + 分段进度条；**不渲染 tail 节点**。
- 子任务卡渲染：标题 + 状态徽标 + 可折叠日志（复用 `log-details` / `log-list`）+ 每子任务独立耗时；失败节点红色 + error 文本。
- **子卡日志不自动开合**：`pending / processing / completed / error / interrupted` 之间的状态迁移只更新徽标、摘要行和列表内容，不修改 `details.open`；默认收起，只有用户点击才展开/收起。这样每个 md 开始/完成时卡片高度稳定，不推动整个导入列表跳动。收起状态下摘要行必须能表达「当前步骤 + 已耗时」，失败原因用卡片内独立 error 块展示，不能只藏在展开区里。
- 耗时口径：child 的 `startedAt` 取首条 `processing` 事件的本地到达时间；`stoppedAt` 取 `complete` / `failed`；父终态时给 `interrupted` 打上停止时间。fork 到首条 processing 之间的排队时间不计入 child 耗时（父卡可看到 fork 后的整体等待）。
- 中断态是**前端派生**（父终态时仍未终态），不是后端状态值；不要新增 `interrupted` 到 `TaskStatus`。

## 6. 边界与失败矩阵

| 场景 | 后端行为 | SSE | 前端表现 |
| --- | --- | --- | --- |
| ZIP 含 1 篇 md | 正常 fork 1 个 child | `fork` + 1 组 `child-progress` | 父卡 + 1 张子卡（不做特例折叠；后续可评审） |
| ZIP 含 0 篇 md | `node_process_md_zip` 抛错，未 fork | 父 failed + error + close | 父卡失败，无子卡 |
| 同名 md（stem 重复） | `_check_unique_stems` 抛错，未 fork | 父 failed + error | 父卡失败，无子卡；提示改名 |
| ZIP 路径越界 | 解压阶段抛错，未 fork | 父 failed + error | 父卡失败，无子卡 |
| 某篇图片缺失 | 该 child 在 `node_md_img` 失败 | child failed（含 failed_list）→ 父 failed → close | 失败子卡 + 兄弟「未完成」 |
| 某篇 embedding 超时 | 该 child 在 `node_document_embedding` 失败 | 同上 | 同上 |
| 父任务失败时其它分支仍在跑 | 迟到 child 推送被父终态抑制 | 不再进入流 | 无「诈尸」更新 |
| SSE 连接晚于 fork | 事件已在队列中，连接后按序消费 | fork 不丢 | 子卡先出现再更新 |
| SSE 在 fork 后断开 | 图继续执行；队列被清理 | 后续 sse_push 无队列，静默丢弃 | 前端连接错误，按现状提示；刷新后任务卡丢失 |
| 客户端在 fork 前断开 | 图继续执行；fork 注册成功但推送丢弃 | 无 | 无卡片；文档仍会完成入库 |
| 刷新页面 | 进程内任务状态不持久化 | — | 任务卡丢失（现状） |
| 同时上传多个 ZIP | 各自父 task_id / child 前缀隔离，锁串行化更新 | 各自队列 | 多张父卡互不干扰 |
| 100 篇 md | fork 载荷含 100 条元数据（仅标题/路径） | 单条 fork + 300 组 `child-progress` | 列表滚动，暂不做虚拟化；需在验收时压测 |
| 多 uvicorn worker | 各进程独立，child 注册表不共享 | 跨进程不一致 | 现状限制；保持单 worker 或后续改造为 Redis |
| 标题含 HTML / 脚本 | 后端原样返回 stem | — | 前端必须文本插值（React 默认转义），不得 `dangerouslySetInnerHTML` |

## 7. 验收清单

### 7.1 协议 / 后端

1. 上传含 N 篇 md 的 ZIP，SSE 事件序列为：父 `progress(processing)` → 父 `progress`（解压完成）→ `fork`（N 条）→ N 组 `child-progress` → 父 `progress(complete)` → `__close__`。
2. `fork.children` 顺序与 `_find_md_files` 的相对路径排序一致；`child_id` 两两唯一，且以父 `task_id` 为前缀。
3. 任意时刻，某个 child 的 `done_list` / `running_list` 不包含其它 child 节点；同一 child 内节点不重复。
4. 父任务 `done_list` 只含 `识别文档类别` / `处理 Markdown 压缩包`，不出现 tail 节点。
5. 每个 child 正常结束时都只有一次 `complete` 事件；父 `complete` 前所有 child 已终态。
6. 单篇 md 失败时，先收到该 child 的 `failed`（`failed_list` 指向具体节点），再收到父 `error` + `__close__`；父终态后新发起的 child 推送被抑制（已在途的事件可能先于 close 到达，前端应按终态忽略）。
7. 0 md / 同名 / zip-slip 均在 fork 前失败，无 `fork` 事件。
8. PDF / 独文件 md 的 SSE 与改造前一致（父 `progress` 仅在失败时新增可选 `failed_list`；失败节点不再误记为 done）。
9. Milvus `minirag_docs.task_id` 仍为父 `task_id`；MinIO 对象路径不变；`file_title` 仍为 md stem。
10. 多分支并发（≥ 10 篇）压测无重复节点、无丢失 child、无死锁；`fork` 到首个 `child-progress` 的顺序稳定。

### 7.2 前端

11. ZIP 上传后先看到父卡；fork 后出现 N 张子卡，顺序稳定，初始「等待中」；子卡随进度独立更新。
12. 父卡聚合计数与分段进度条与 child 状态一致；父卡不显示 tail 节点。
13. 失败时只有失败 child 显示红色节点与 error；其它未完成 child 显示「未完成」，不继续计时。
14. 旧后端（无 fork / child-progress）时回退为现有单卡；旧前端忽略 `fork` / `child-progress` 不报错，父卡不被子进度覆盖。
15. `npm run build`（`tsc --noEmit` + vite）通过；浏览器 console 无报错；390 / 720 / 1280、Light / Dark 正常。

## 9. 备选方案与被否决项

| 方案 | 为什么不用 |
| --- | --- |
| 在节点名前拼 md 标题（`Markdown 图片识别（xxx）`） | 仍是平铺列表，无独立状态；标题长度不可控；失败归因靠字符串 |
| 在父 `done_list` 中保留 N 份同名节点 | 前端无法区分；去重逻辑与现有 UI 都假设节点名唯一；列表会迅速膨胀 |
| 前端 JSZip 解压后自行分叉 | 与后端实际接受的 md 列表可能不一致；重复实现图片/路径校验；无进度归属 |
| 每个 md 一条 SSE / 一个队列 | N 条连接、N 个生命周期、重连与清理复杂；单流加 `child_id` 已足够 |
| 新增 `/upload/children/{task_id}` 查询接口 | 仍需事件推送；多一套状态同步与轮询；当前进程内状态也不适合做查询源 |
| 每篇 md 使用独立业务 `task_id` | 会改变 Milvus / MinIO / 清场语义，风险远大于收益 |
| 在 `zip_fanout_router` 里发 fork | 路由函数有副作用、难测试；且节点 done 与 fork 的顺序语义不显式 |
| 在 `node_process_md_zip` 末尾发 fork | 可行但语义混杂；父节点尚未完成推送时就出现子卡，且复用 `md_tail`/`pdf` 时需要额外分支 |
| 用 `asyncio.Task` + 轮询子图状态 | 引入并发控制与取消语义，与 P2 纠缠；本需求不需要 |

## 10. 风险、限制与待确认

1. **进程内状态**：`task_utils` 的四个字典是进程级、无淘汰；新增 child 注册表会放大内存占用。当前保持单 worker 假设；多 worker / 长跑场景需迁 Redis 或独立任务服务（已有 TODO，不在本方案解决）。
2. **断线不重放**：SSE 是单次流，前端断线重连不会收到历史 fork；现有机制如此。若要支持，需要事件缓冲 / 查询接口，另开需求。
3. **父失败后的兄弟分支**：LangGraph 不会强杀线程，兄弟分支可能在父失败后继续写；本方案只保证父终态后**新发起**的进度推送被抑制，不解决写入回退（P2）。由于 `set_task_status` 与在途线程的 `sse_push` 不是同一原子操作，极小概率下会有一条已构造好的 child 事件先于 `__close__` 到达；前端收到父 `error` 后应停止消费子事件。
4. **fork 事件丢失**：如果 SSE 队列在 fork 前被移除，前端只能看到父卡；子任务仍执行完成，文档列表照常刷新。这种降级可接受，但需要前端对「收到 `child-progress` 却没有对应 child」做防御（忽略 + console.warn）。
5. **单 md ZIP 的卡片形态**：当前决定统一 fork（父 + 1 子）。若评审认为冗余，可后续在前端折叠为单卡，后端协议不变。
6. **P2 兼容**：P2 若新增 `cancelled` 状态，`_TERMINAL` 与 `task_push_sse` 的父终态抑制需要把 `cancelled` 纳入；child 的「未完成」仍由前端派生，不冲突。
7. **事件名 `fork`**：与操作系统进程 fork 无关，仅是 SSE 协议事件名；已在 `SSEEvent` 常量中注释清楚。

## 附录 B · 关键顺序证明（实现时核对）

1. `node_process_md_zip` 是 `@trace_node(need_push=True)`；其 `add_done_node` 在函数返回后、图调度下一节点前执行 → fork 事件一定晚于父解压完成事件。
2. `node_md_fork` 在返回前调用 `fork_task`，`sse_push` 入队是同步的；`zip_fanout_router` 在此之后才构造 `Send` → fork 一定早于任何分支的 `add_running_node`。
3. 每个分支的 `node_md_tail_branch` 在 `md_tail_processor.invoke` 返回后调用 `complete_child`，再返回父图；`ainvoke` 汇总全部分支后才返回 → 父 `complete` 一定晚于所有 child `complete`。
4. 父异常时先 `set_task_status(FAILED)` 再推送；此后 `task_push_sse(child)` 读取父状态并丢弃 → 晚到的 child 事件不会污染已关闭的 UI。
