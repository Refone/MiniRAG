## 1. 验收

1. **查询停止**：查询进行中（含等待首个 delta）发送按钮变为停止按钮；点击后按钮进入「中止中」，服务端受理后卡片状态变「已中止」，按钮复位回发送。
2. **查询终态**：中止后不再追加 delta；已生成的半截答案保留在消息内并追加「已中止本次查询」；不落库半截助手消息（刷新后不出现半截答案）。
3. **查询复位**：中止后 `sending=false`，可立即发起下一次查询；旧 SSE 仍按任务 id 隔离，不污染新卡片。
4. **导入停止**：导入任务卡片（处理中）出现中止按钮；点击后徽标显示「中止中…」，中止完成后显示「已中止」。
5. **导入回退**：中止被受理时，Milvus 无本任务 `docs/chunks` 行；MinIO 无本任务图片目录与三份制品；本地 `output/uploads` 与 `output/import` 临时产物清理；文档列表自动刷新后无半成品。
6. **同名覆盖安全**：对已存在同名文档重新导入，在覆盖动作开始之前中止，旧文档的行 / 三份制品 / 图片保持可用（不被误删）。
7. **覆盖拒绝**：同名覆盖写区一旦开始，中止请求返回 `aborted=false, reason="overwrite"`，任务继续跑完并正常入库；前端提示「同名文档正在覆盖入库，当前无法中止」。新建型写区则允许中止，跑完后整体回退。
8. **幂等**：重复中止请求幂等；已完成任务返回 `aborted=false` + 终态；中止过程中不重复触发回退。
9. **SSE 契约**：查询 / 导入均新增 `aborted` 事件，随后 `__close__` 关流；前端据此收尾，不出现卡在「中止中」或 `sending` 永真的情况。
10. **不回归**：P1 卡片宽度/中线/吸底按钮/高水位滚动行为不变；按钮开关切换不引起布局跳动；390 / 720 / 1280、Light / Dark 正常。
11. **构建**：`npm run build`（`tsc --noEmit` + vite）通过，浏览器 console 无报错。

## 2. 现状与约束（调研结论）

### 2.1 任务与 SSE

| 维度 | 查询任务 | 导入任务 |
| --- | --- | --- |
| 触发 | `POST /api/query`（sync 路由 + `BackgroundTasks`） | `POST /api/upload`（async 路由 + `BackgroundTasks`） |
| 任务键 | `session_id`（前端生成，复用为 trace id） | `task_id`（服务端 `uuid4().hex`） |
| SSE | `GET /api/query/sse/{session_id}` | `GET /api/upload/sse/{task_id}` |
| 执行 | `arun_query` → `query_processor.ainvoke`（6 节点） | `arun_import` → `import_processor.ainvoke`（7 节点，含 md_tail 子图与 zip 扇出） |
| 进度 | `utils/task_utils.py` 进程内字典 + `progress` 快照 | 同左 |
| 状态值 | `pending / processing / complete / failed` | 同左 |

两份 SSE 事件目前只有 `ready / progress / delta / final / error / __close__`，`sse_generator` 只在 `__close__` 时结束流。

### 2.2 为什么不能直接 `asyncio.Task.cancel()`

- 任务由 FastAPI `BackgroundTasks` 调度，**没有可取消的句柄**。
- LangGraph 1.2.12 把同步节点放进线程池执行（`langgraph/pregel/_call.py` 使用 `run_in_executor`）。取消 asyncio 任务只会让等待方立刻抛 `CancelledError`，**线程内的节点会继续跑完**。
- 本地最小图实测：一个并行分支抛异常时 `ainvoke` 约 0.01s 就返回，其它分支的线程仍在后台继续跑完（`ainvoke` 返回后 0.5s 仍能观察到它们写入的副作用）。

因此中止必须是**协作式**的：线程内主动检查取消标记，在检查点抛异常退出；同时对「覆盖同名旧文档」的写区做握手保护，避免「先回退、后被在途线程写回」。

### 2.3 长耗时点与中止粒度

| 链路 | 长耗时点 | 上限（`app_config` / 客户端） | 中止生效粒度 |
| --- | --- | --- | --- |
| 查询 | 查询重写 LLM | 90s 超时 + 1 次重试 | 调用返回后的检查点 |
| 查询 | Milvus 文档/切片检索 | 30s | 节点边界 |
| 查询 | MCP 联网搜索 | 60s | 节点边界 |
| 查询 | 答案流式输出 | 逐 token | **每个 chunk**，最快 |
| 导入 | MinerU 转换轮询 | `10s × 页数 + 30s` | **每轮轮询**（5s 间隔） |
| 导入 | VLM 图片摘要 | 60s × 并发 8 | 每批结果 |
| 导入 | 切片向量化 | 按 batch 并发 8 | 每批提交前 |
| 导入 | 关键词/摘要 LLM | 90s | 调用返回后的检查点 |
| 导入 | Milvus / MinIO 写入 | 秒级 | **覆盖型写区不可中止**；新建型写区可中止，跑完后回退（见 §4） |

> 中止不是「强杀」：在途的 LLM / VLM / embedding 调用不会被网络层取消，最坏要等一次调用返回（≤ 对应超时）。UI 用「中止中」覆盖这段等待，不用假成功。

### 2.4 副作用清单（决定回退范围）

| 时机 | 查询 | 导入 |
| --- | --- | --- |
| 执行中 | Mongo `chat_history` 写 user 消息（意图识别节点第 6 步） | 本地 `output/uploads/<原文件名>`、`output/import/<stem>/`、`<stem>.zip` |
| 图片阶段 | — | MinIO `markdown-images/<file_title>/…`（旧代码先 `clear_dir_if_exist` 再上传） |
| 写区（入库） | — | MinIO 三份制品（origin / markdown / chunks）+ Milvus `minirag_docs` / `minirag_chunks` |
| 收尾 | Mongo 写 assistant 消息 + SSE `final` | 无 |

**关键事实**：`node_document_embedding` 当前顺序是「先删同名旧文档 → 再上传制品 → 再插库」。删除动作不可逆——一旦开始，旧文档就没了。这决定了覆盖动作一旦开始就不能再接受中止（§4.2）；新建型写区不影响旧文档，可以中止后回退。

## 4. 核心语义

### 4.1 终态与事件

- `TaskStatus` 新增 `CANCELLED = "cancelled"`（`utils/task_utils.py`）。
- `SSEEvent` 新增 `ABORTED = "aborted"`（`utils/sse_utils.py`）。
- 中止受理后的推送顺序固定为：

```text
progress  {"status": "cancelled", "done_list": [...], "running_list": []}
aborted   {"status": "cancelled", "rollback_ok": true|false}   # rollback_ok 仅导入
__close__ {}
```

- 查询卡片 / 导入徽标都新增「已中止」终态：卡片可关闭（查询），列表刷新 + toast（导入）。

### 4.2 可中止窗口与「写区」

`node_document_embedding` 的写入段（删旧同名 → 传三份制品 → 插 docs → 插 chunks → 清旧图片）秒级完成，但其中**覆盖同名旧文档**的动作不可逆。因此把写区再分两类：

```text
可中止区（长耗时，随时可停）                    写区（秒级）
PDF 转换 / 图片识别 / 切分 / 元数据 LLM     ->  新建文档：删孤儿 → 传制品 → 插 docs → 插 chunks
/ 向量化                                         （可中止：跑完后整体回退本任务新建对象）
                                                 覆盖文档：删旧同名 → 传制品 → 插 docs → 插 chunks
                                                 （不可中止：一删旧文档就回不去）
```

- **写区**：`node_document_embedding` 中从第一次写操作到写完 chunks 的连续段落，内部无检查点。
- **覆盖型写区**：进入写区前 `query_doc_rows_by_file_title(file_title)` 非空（同名旧文档存在），写区会删除旧行与旧制品。只有覆盖型写区会拒绝中止。
- **新建型写区**：预检无同名旧文档，写区只创建本任务的新对象；中止时整体回退，没有旧数据可伤。
- 两把闸共用同一把 `runtime.lock`，保证「要么在中止前拦下覆盖、要么覆盖开始后拒绝中止」，不存在中间态：

```python
# 节点进入写区（原子；destructive=该标题是否已存在同名旧文档）
def begin_write(task_id: str, where: str, *, destructive: bool) -> None:
    rt = _runtimes.get(task_id)
    if rt is None:
        return                      # 脚本直跑无 runtime：不干预
    with rt.lock:
        if rt.abort_event.is_set():
            raise TaskCancelled(task_id, where)   # 中止已受理：覆盖不能开始
        rt.writes_in_flight += 1                   # 回退前要等它结束
        if destructive:
            rt.destructive_started = True          # 之后中止一律拒绝

def end_write(task_id: str) -> None:               # 节点里 try/finally 调用
    rt = _runtimes.get(task_id)
    if rt is None:
        return
    with rt.lock:
        rt.writes_in_flight = max(0, rt.writes_in_flight - 1)
        rt.writes_done.notify_all()

# 中止受理（原子；只有覆盖型写区会拒绝）
def request_cancel(task_id: str) -> bool:
    rt = _runtimes.get(task_id)
    if rt is None:
        return False
    with rt.lock:
        if rt.destructive_started:
            return False
        rt.abort_event.set()
        return True
```

> **为什么还要 `writes_in_flight`**：中止被受理时，可能有另一个「新建型」分支正处在写区里（zip 扇出）。LangGraph 在某个分支抛异常后会立即返回，但该分支的线程仍在写。回退前用 `wait_writes_idle(runtime, timeout)` 等所有在途写区结束（新建型写区秒级），再开始清理；超时只告警，不阻塞收尾。

**不变量（实现后逐条核对）**

1. 中止被受理（`aborted=true`）⇒ 本任务**没有开始过任何覆盖型写区**（旧文档的行 / 制品 / 图片均未被触碰）。
2. 覆盖型写区一旦开始 ⇒ 后续中止请求一律拒绝（`destructive_started` 不重置），任务必须跑完或按原有失败语义结束。
3. 中止受理后，可能已有**新文档**分支写完：允许，回退时按 `task_id` 删除本任务的新行、新制品、新图片即可（没有旧数据可伤）。
4. 图片对象路径带 `task_id` ⇒ 中止清理只删本任务目录，永不误删同名旧文档的图片（失败不清理）。
5. 中止回退幂等：重复执行结果一致，可安全跑两遍（见 §5.5）。
6. 回退开始前必须等 `writes_in_flight == 0`（写区分支线程已结束），避免「回退后又写回」。
7. HTTP abort 响应只表示「是否受理」；最终状态以 SSE 终态为准。

### 4.3 状态机

```text
查询：
idle --send--> running --progress--> running
running --点击停止--> aborting --受理--> cancelled --aborted--> 卡片「已中止」/ 消息「已中止本次查询」
running --final/__close__--> completed
running --error/断连--> failed
aborting --任务已完成--> completed（以 final/__close__ 为准，前端只清中止态）

导入：
uploading --POST /upload--> pending --progress--> processing
processing --点击中止 & 未开始覆盖型写区--> aborting --受理--> cancelled（回退完成后再推 aborted）
processing --点击中止 & 已开始覆盖型写区--> 拒绝（aborted=false / overwrite），继续 processing
processing --__close__/complete--> completed
processing --error--> failed
```

## 5. 后端设计

### 5.1 新模块 `src/utils/task_control.py`

职责：运行中任务登记、取消标记、写区/覆盖握手、检查点、批次可中断睡眠、图片目录登记。

```python
class TaskCancelled(Exception):
    """协作式中止信号；由检查点抛出，沿 LangGraph 冒泡到 service。"""


@dataclass(eq=False)
class TaskRuntime:
    task_id: str
    kind: str                                   # "query" | "import"
    abort_event: threading.Event = field(default_factory=threading.Event)
    lock: threading.RLock = field(default_factory=threading.RLock)
    destructive_started: bool = False           # 已开始覆盖型写区（中止拒绝）
    writes_in_flight: int = 0                   # 在途写区数（回退前等它归零）
    writes_done: threading.Condition = field(init=False)
    origin_file_path: str = ""                  # 导入：POST /upload 落盘路径，回退用
    image_titles: set[str] = field(default_factory=set)   # 已登记图片目录的 file_title

    def __post_init__(self) -> None:
        # 与 lock 共用同一把锁；end_write 里 notify_all 唤醒 wait_writes_idle
        self.writes_done = threading.Condition(self.lock)

_runtimes: dict[str, TaskRuntime] = {}

def register(task_id: str, kind: str, origin_file_path: str = "") -> TaskRuntime
def get(task_id: str) -> TaskRuntime | None
def release(runtime: TaskRuntime) -> None       # 身份校验后删除，避免误删新任务的 runtime
def request_cancel(task_id: str) -> bool        # §4.2
def begin_write(task_id: str, where: str, *, destructive: bool) -> None   # §4.2
def end_write(task_id: str) -> None                                        # try/finally
def wait_writes_idle(runtime: TaskRuntime, timeout: float = 10.0) -> bool
def is_cancelled(task_id: str) -> bool
def checkpoint(task_id: str, where: str = "") -> None
    # runtime 不存在 / 未取消 → 静默返回；已取消 → raise TaskCancelled
def mark_image_title(task_id: str, file_title: str) -> None
def image_titles(task_id: str) -> set[str]
def sleep_with_cancel(seconds: float, task_id: str, step: float = 0.2) -> None
    # 分片 sleep，每片 checkpoint；用于 MinerU 长等待
def path_in_use(origin_file_path: str, exclude: str) -> bool
    # 回退本地文件前判断是否被其它并发任务占用（同名上传场景）
```

设计要点：

- 与 `task_utils` 分离：`task_utils` 管「进度/状态」，`task_control` 管「取消/写区/产物登记」，互不依赖。
- 全部进程内单例，与现有 `task_utils` 相同的单 worker 前提；多 worker 需外置存储，本 Phase 不做。
- `checkpoint` 的查找失败必须是静默 no-op：`node_*.py` 的 `__main__` 直跑、离线脚本都没有 runtime。
- `image_titles` 的读写也在 `runtime.lock` 内（zip 多分支会并发登记），避免并发 `set` 丢写。
- 同 id 重复 `register` 覆盖旧 runtime 并返回新对象；`release` 用 `is` 身份校验，避免旧任务误删新任务的 runtime。

### 5.2 节点统一接入（`src/utils/node_utils.py`）

```python
def trace_id(state) -> str:
    if "task_id" in state:
        return state["task_id"]
    if "session_id" in state:
        return state["session_id"]
    return "-"

def checkpoint_state(state, where: str) -> None:
    """节点内检查点：查询用 session_id、导入用 task_id，无需调用方关心。"""
    task_control.checkpoint(trace_id(state), where)
```

`_task_trace` 的包装改为：

1. 入口先 `task_control.checkpoint(tid, "node-enter")`——节点起跑前统一拦截；
2. `TaskCancelled` 直接上抛，**不补 `add_done_node`**（被中断的节点不算完成；状态由 `mark_cancelled` 收口）；
3. 其它异常保持现状（`add_done_node` 后 re-raise）；
4. `node_log` / `step_log` 对 `TaskCancelled` 记 INFO「节点中止 / 步骤中止」后原样上抛，**不打印错误堆栈**——中止是预期路径，不能污染 ERROR 日志。

这样所有 13 个节点自动获得「节点边界可中止」，个别长节点再按 §5.3 / §5.4 增加内部检查点。

### 5.3 查询链路

#### 5.3.1 `arun_query`（`src/service/query_service.py`）

```python
async def arun_query(session_id, query, enable_web_search=True, enable_hyde=True, runtime=None):
    runtime = runtime or task_control.register(session_id, "query")
    try:
        clear_task(session_id)                                # 先清旧任务，再判中止
        task_control.checkpoint(session_id, "query-start")   # aborted 早于任务启动
        set_task_status(session_id, TaskStatus.PROCESSING.value)

        end_state = await query_processor.ainvoke(create_state(...))
        sse_push(session_id, SSEEvent.CLOSE, {})
        set_task_status(session_id, TaskStatus.COMPLETE.value)
        return end_state
    except TaskCancelled:
        task_utils.mark_cancelled(session_id)                # status=cancelled + 清 running + 推 progress
        sse_push(session_id, SSEEvent.ABORTED, {"status": "cancelled"})
        sse_push(session_id, SSEEvent.CLOSE, {})
        logger.info("查询任务已中止: session_id={}", session_id)
        return {}
    except Exception as e:
        ...                                                  # 保持现状：failed + error 事件
    finally:
        task_control.release(runtime)
```

- **不在 `ainvoke` 返回后补判取消**：`final` 由答案节点在 graph 内推送，若此时再判取消会出现「先 final 后 aborted」的自相矛盾；graph 正常返回即视为已完成（中止太晚，以完成为准）。
- `except Exception` 里若 `task_control.is_cancelled(...)` 为真（中止与异常竞态），与 `TaskCancelled` 走同一个 `_finish_cancelled()`，避免用户已点停止却看到「失败」。
- 查询没有不可逆写入，中止不删除 Mongo 里的 user 消息：**中止发生在意图识别落库之后时，问题保留；之前则不落库**。半截答案只在内存，不写库。
- 查询任务注册在路由里完成（早于后台任务启动），保证「点了发送立刻点停止」也能命中。

### 5.4 导入链路

#### 5.4.1 `arun_import`（`src/service/import_service.py`）

```python
async def arun_import(task_id, origin_file_path, runtime=None):
    runtime = runtime or task_control.register(task_id, "import", origin_file_path)
    try:
        task_utils.clear_task(task_id)                        # 先清旧任务，再判中止
        task_control.checkpoint(task_id, "import-start")
        task_utils.set_task_status(task_id, TaskStatus.PROCESSING.value)

        end_state = await import_processor.ainvoke(initial_state)

        # 完成事件由本函数推送（不像查询的 final 在 graph 内），
        # 因此可以安全地补一次检查：受理中止后立刻收尾，避免「已受理却推完成」
        task_control.checkpoint(task_id, "import-after-graph")

        # 成功路径（原逻辑，放在 try 内，保证 release 前状态已落定）
        task_utils.set_task_status(task_id, TaskStatus.COMPLETE.value)
        task_utils.set_task_result(task_id, "result", "ok")
        task_utils.task_push_sse(task_id)
        sse_push(task_id, SSEEvent.CLOSE, {})
        logger.info("导入任务完成: task_id={}", task_id)
        return end_state
    except TaskCancelled:
        task_utils.mark_cancelled(task_id)
        await asyncio.to_thread(task_control.wait_writes_idle, runtime, 10.0)
        rollback_ok = await _rollback_with_settle(runtime)          # to_thread + 两遍
        sse_push(task_id, SSEEvent.ABORTED, {"status": "cancelled", "rollback_ok": rollback_ok})
        sse_push(task_id, SSEEvent.CLOSE, {})
        logger.info("导入任务已中止: task_id={}, rollback_ok={}", task_id, rollback_ok)
        return {}
    except Exception as e:
        task_utils.set_task_status(task_id, FAILED)
        task_utils.task_push_sse(task_id)              # 先让卡片变「失败」
        sse_push(task_id, SSEEvent.ERROR, {"error": str(e)})
        sse_push(task_id, SSEEvent.CLOSE, {})
        logger.exception("导入任务失败: task_id={}", task_id)
        raise
    finally:
        task_control.release(runtime)
```

- **失败不自动回退**（与现状一致）：覆盖型失败可能已删旧文档，新建型失败可能留半成品；本 Phase 只把中止纳入回退，失败清理不在范围内。新建型失败留下的图片目录属于孤儿对象，下次同名导入收尾会清掉（§5.4.3）。
- `except Exception` 里若 `task_control.is_cancelled(...)` 为真（中止与异常竞态），与 `TaskCancelled` 走同一个 `_finish_cancelled()`（含回退），不要报「失败」。
- `rollback_ok=false` 不改变任务终态（仍是 cancelled），只让前端额外提示「部分数据清理失败」。

#### 5.4.5 `node_document_embedding` 重排（写区成型）

把**长耗时、无写入**的步骤全部前移，写区只保留写入；并在进入写区前预检同名旧文档，决定本次写区是否「覆盖型」：

```text
旧：校验 → 删旧文档 → 上传制品 → LLM 关键词/摘要 → 向量化 → 插 docs → 插 chunks
新：校验 → 读 md / chunks.json → LLM 关键词/摘要 → 向量化
    → old_rows = query_doc_rows_by_file_title(file_title)   # 判断是否同名覆盖
    → begin_write(destructive=bool(old_rows))               # 覆盖型：之后不可中止
    → try: 删旧同名文档（行 + 三份制品；非覆盖型时只清理孤儿）
    →      上传三份制品
    →      插 docs（拿到 doc_id）→ 插 chunks
    →      clear_doc_images_except(file_title, task_id)      # 删旧图片目录，失败仅告警
    → finally: end_write(task_id)                           # 让回退可以安全开始
```

- 写区预计 < 3s（Milvus 删除/插入 + 3 个 MinIO PUT）；覆盖型窗口更短，新建型即使命中也可回退。
- 同名覆盖语义不变：仍是「旧行 + 旧制品删除 → 写新行」；区别只是发生的时刻更晚、区间更短。
- `begin_write` 放在删除动作之前，且与 `request_cancel` 共用锁：中止先到 → 一个字节都不写；覆盖先到 → 拒绝中止。
- 写区后任务必然成功；若抛异常则走失败语义（不回退），与现状一致。

### 5.5 中止回退 `src/service/import_rollback.py`（新增）

#### 5.5.1 回退范围

| 对象 | 处理 | 说明 |
| --- | --- | --- |
| Milvus `minirag_chunks` | 按 `doc_id` 删除 | 中止受理后已完成的「新建型」分支会有本任务行，属正常路径 |
| Milvus `minirag_docs` | 按 `task_id` 删除 | 只可能是新建型分支；中止被受理时覆盖型写区不可能已开始 |
| MinIO 图片 | `<image_dir>/<file_title>/<task_id>/` 整目录删 | 标题来自 `runtime.image_titles` ∪ 库行 |
| MinIO 三份制品 | 按本任务库行的标题清整目录 | 覆盖型写区未开始 ⇒ 该标题没有旧文档，整目录删除只会删到本任务新建的制品 |
| 本地 `output/uploads/<原文件名>` | 删除 | 被其它并发任务占用时跳过 |
| 本地 `output/import/<stem>/`、`<stem>.zip` | 递归删除 | 覆盖 PDF / 独立 md / zip 三种链路；被占用时跳过 |

```python
@dataclass
class RollbackReport:
    docs: int = 0          # 本次删除的 docs 行数（已写完的新建型分支）
    chunk_docs: int = 0    # 被删 chunks 涉及的 doc_id 数
    images: int = 0
    local_ok: bool = True
    errors: list[str] = field(default_factory=list)

    @property
    def ok(self) -> bool:
        return not self.errors


def rollback_import(runtime: TaskRuntime) -> RollbackReport:
    report = RollbackReport()
    task_id, titles = runtime.task_id, set(runtime.image_titles)
    rows: list[dict] = []

    # 0) 按 task_id 查本任务已写入的行（新建型分支可能已写完）
    try:
        rows = MILVUS_CLIENT.query_docs_by_task_id(task_id)
        if rows:
            logger.info("中止回退清理已写入行: task_id={}, rows={}", task_id, len(rows))
            doc_ids = [row["id"] for row in rows]
            MILVUS_CLIENT.delete_chunks_by_doc_ids(doc_ids)
            MILVUS_CLIENT.delete_docs_by_task_id(task_id)
            report.docs, report.chunk_docs = len(rows), len(doc_ids)
            titles.update(row["file_title"] for row in rows)
    except Exception as e:
        report.errors.append(f"milvus: {e}")

    # 1) MinIO：仅本任务图片目录（绝不按标题整目录删）
    for title in titles:
        try:
            report.images += MINIO_CLIENT.clear_dir_if_exist(
                f"{ENV_CONFIG.minio.image_dir}/{title}/{task_id}/"
            )
        except Exception as e:
            report.errors.append(f"images[{title}]: {e}")

    # 2) 三份制品：按本任务库行的标题清（覆盖型未开始 ⇒ 该标题无旧文档）
    for title in {row["file_title"] for row in rows}:
        try:
            MINIO_CLIENT.clear_doc_artifacts(title)
        except Exception as e:
            report.errors.append(f"artifacts[{title}]: {e}")

    # 3) 本地临时产物（被其它并发任务占用时跳过）
    try:
        report.local_ok = _cleanup_local(task_id, runtime.origin_file_path)
    except Exception as e:
        report.local_ok = False
        report.errors.append(f"local: {e}")

    return report
```

#### 5.5.2 两遍扫描（在途上传）

LangGraph 在一个分支抛异常后会立即返回，其它扇出分支的线程可能仍在跑（§2.2 实测）。单遍清理可能被「晚到的图片 PUT / 本地写文件」重新留下痕迹，因此：

```python
ROLLBACK_SETTLE_SECONDS = 1.5

async def _rollback_with_settle(runtime) -> bool:
    first = await asyncio.to_thread(rollback_import, runtime)     # 立即清一遍
    await asyncio.sleep(ROLLBACK_SETTLE_SECONDS)                  # 给在途上传收尾
    second = await asyncio.to_thread(rollback_import, runtime)    # 幂等再清一遍
    return first.ok and second.ok
```

- 回退是阻塞 IO（Milvus / MinIO / 磁盘），必须 `asyncio.to_thread`，不能卡住 FastAPI 事件循环（`import_rollback.py` 自身保持同步，`asyncio` 只在 service 里用）。
- 回退前先 `wait_writes_idle(runtime, timeout=10)`：等待其它分支的在途写区结束（新建型秒级；覆盖型不会与中止共存）。超时只告警，仍继续清理。
- 超过 1.5s 的极端慢上传仍可能留下孤儿图片目录；它不在库里、不指向任何文档，且下次同名导入收尾会清掉（§5.4.3），因此只记日志，不阻塞中止。
- 写区内的写入由 `wait_writes_idle` 保证已结束；两遍扫描只用于兜底在途的图片上传 / 本地写文件，不会出现「回退后又写回库行」。

```python
class AbortResponse(BaseModel):

    aborted: bool
    task_status: str = ""
    reason: str = ""
```

路由实现要点：

```python
@router.post("/query/{session_id}/abort", response_model=AbortResponse, status_code=202)
def abort_query(request: Request, session_id: str) -> AbortResponse:
    logger.info(f"[{str(request.url)}] 请求中止查询")
    return _abort_response(session_id)

@router.post("/upload/{task_id}/abort", response_model=AbortResponse, status_code=202)
def abort_upload(request: Request, task_id: str) -> AbortResponse:
    logger.info(f"[{str(request.url)}] 请求中止导入")
    return _abort_response(task_id)

_TERMINAL = {"complete", "failed", "cancelled"}

def _abort_response(task_id: str) -> AbortResponse:
    status = task_utils.get_task_status(task_id)
    if status in _TERMINAL:
        # 终态直接拒绝，不再设置取消标记（避免「已受理但任务早已结束」的歧义）
        return AbortResponse(aborted=False, task_status=status, reason="not_running")

    runtime = task_control.get(task_id)
    aborted = task_control.request_cancel(task_id)     # 只有覆盖型写区会返回 False
    if aborted:
        reason = ""
    elif runtime is None:
        reason = "unknown_task"
    elif runtime.destructive_started:
        reason = "overwrite"
    else:
        reason = "not_running"
    return AbortResponse(aborted=aborted, task_status=status, reason=reason)
```

- 两个 abort 路由都放在既有 SSE 路由之后即可（路径段不同，无匹配冲突）。
- `POST /api/query` / `POST /api/upload` 在 `sse_create_queue` 之后、`add_task` 之前 `task_control.register(...)`，并把 runtime 传给 service；`arun_*` 里的 `runtime=None` 分支仅服务脚本直跑。
- 不引入 `asyncio.create_task`：取消是协作式的，`BackgroundTasks` 已满足调度需求，保持最小改动。

### 5.7 进度 / 状态收口（`src/utils/task_utils.py`）

```python
class TaskStatus(StrEnum):
    ...
    CANCELLED = "cancelled"

def mark_cancelled(task_id: str) -> None:
    """中止收口：状态置 cancelled、清空 running、推一次 progress。"""
    set_task_status(task_id, TaskStatus.CANCELLED.value)

```

- 中止后不再有节点推送（graph 已退出）；`done_list` 保留已完成步骤，供卡片展示「停在哪一步」。

## 6. 前端设计

### 6.1 查询：发送按钮 ⇄ 停止按钮

#### 6.1.1 交互

| 状态 | 按钮 | 行为 |
| --- | --- | --- |
| 空闲 / 已完成 | `↑` 发送（现状） | 发送 |
| `sending && !aborting` | `■` 停止 | 点击 → `abort()`，立即进入中止中 |
| `sending && aborting` | 加载环（禁用） | 等待服务端终态；防重复点击 |
| 中止完成 | 复位 `↑` | 可继续提问 |

- 尺寸仍为 32×32，位置不变（`.send` 的布局完全复用），只有颜色/图标/禁用态变化 → 不引起 footer 重排。
- 点击停止后**冻结 delta**（不再追加半截文本），避免「已停止却还在长」的错觉；`final` / `aborted` / `__close__` 仍正常处理。

#### 6.1.3 `chatStore`

```ts

  // ...
  aborting: boolean;
  abort: () => Promise<void>;
}
let abortRequested = false;   // 模块级：本次请求已受理中止，用于冻结 delta
```

- `send()` 开头 `abortRequested = false`、`set({ aborting: false })`；`onDelta` 增加 `if (abortRequested) return;`。
- `onAborted`：
  - `finishTask("cancelled")`（`QueryTaskView.progress.status = "cancelled"`）；
  - `patchBot({ typing: false, streaming: false, aborted: true })`；
  - `set({ sending: false, aborting: false })`；`abortRequested = false`。
- `onFinal` / `onServerClose` / `onError` 都补 `aborting: false`。`send()` 内维护 `let abortedReceived = false`：

```ts
onAborted: () => {           // 先于 __close__ 到达
  abortedReceived = true;
  abortRequested = false;
  finishTask("cancelled");                 // 卡片状态 = cancelled
  patchBot({ typing: false, streaming: false, aborted: true });
  set({ sending: false, aborting: false });
},
onServerClose: () => {
  // 有 final → 完成；否则受理过中止 → 已中止；其余沿现状按 completed 收尾
  finishTask(finalReceived ? "completed" : abortedReceived || abortRequested ? "cancelled" : "completed");
  set({ sending: false, aborting: false });
  ...
},
```

- `onError` 收尾时若 `abortedReceived || abortRequested`，按 `cancelled` 处理（中止已受理/请求已发出，SSE 先断），否则沿用现状 `finalReceived ? completed : failed`；两种分支都清 `aborting`。
- `finishTask` 的入参联合类型增加 `"cancelled"`；`dismissTask`：`completed / failed / cancelled` 均可关闭。
- `abort()`：

```ts
abort: async () => {
  const { sending, aborting, sessionId } = get();
  if (!sending || aborting) return;
  set({ aborting: true });
  abortRequested = true;
  try {
    const res = await postAbortQuery(sessionId);
    if (!res.aborted) {
      // 未受理（任务刚好完成 / 尚未注册）：解除冻结，交给 SSE 终态收尾
      abortRequested = false;
      set({ aborting: false });
      console.warn(`[chat] 中止未受理：${res.reason || res.task_status}`);
    }
  } catch (e) {
    abortRequested = false;
    set({ aborting: false });
    console.error("[chat] 中止请求失败", e);
  }
},
```

> 不做「超时后前端强制复位」：终态以 SSE 为准；SSE 断开会走 `onError`，不会卡死。请求失败时恢复可点击，用户可再试。

```ts
abortFile: async (fileId) => {
  const file = get().files.find((f) => f.id === fileId);
  if (!file?.taskId || file.aborting) return;
  if (file.status !== "processing") return;
  patchFile(fileId, { aborting: true });
  try {
    const res = await postAbortUpload(file.taskId);
    if (!res.aborted) {
      patchFile(fileId, { aborting: false });
      if (res.reason === "overwrite") {
        get().pushToast("info", "同名文档正在覆盖入库，当前无法中止");
      } else if (res.task_status === "complete") {
        patchFile(fileId, { status: "completed" });
      } else if (res.task_status === "failed") {
        patchFile(fileId, { status: "error" });
      } else if (res.task_status === "cancelled") {
        patchFile(fileId, { status: "cancelled" });
      } else if (res.reason === "unknown_task") {
        // 后端重启 / 任务不存在：本地不可能是「处理中」，标记失败并提示重传
        patchFile(fileId, { status: "error" });
        get().pushToast("error", "任务已不可用（服务可能重启），请重新上传");
      }
    }
  } catch (e) {
    patchFile(fileId, { aborting: false });
    get().pushToast("error", `中止失败：${(e as Error).message}`);
  }
},
```

## 9. 边界 / 已知取舍

| 场景 | 行为 |
| --- | --- |
| 中止点在长模型调用中 | 等调用返回后的下一个检查点生效；最坏 ≤ 一次调用超时（LLM 90s / VLM 60s / MCP 60s），UI 显示中止中 |
| 查询「回答已生成完」瞬间点停止 | 以 `final` / `__close__` 为准按完成处理；前端只清中止态，不覆盖答案 |
| 查询中止后刷新 | 助手消息不落库；用户消息取决于中止时点（意图识别落库之后保留），历史里可能只有问题 |
| 任务未注册就点停止（发送请求尚在途） | 返回 `aborted=false`；前端解除冻结、复位按钮，用户可再点 |
| 导入开始覆盖型写区后点停止 | 拒绝（`reason=overwrite`），任务继续完成；前端 toast 说明 |
| 同名覆盖导入 | 覆盖动作前中止：旧文档完整；覆盖动作一旦开始就不再接受中止，因此不会出现「回退后旧文档也没了」 |
| zip 扇出 | 未开始覆盖型写区时中止：已完成的「新建型」分支会被整体回退；任一分支开始覆盖同名旧文档后整任务拒绝中止 |
| 重复点击 / 重复请求 | 前端 `aborting` 禁用；后端 `request_cancel` 幂等 |
| 后端重启 | 内存 runtime 丢失；中止返回 `aborted=false, reason=unknown_task`；前端提示失败，任务实际已不存在 |
| 浏览器关闭 / 断网 | 任务继续执行（现状）；重开后导入任务列表为内存态，不恢复 |
| 同会话并发查询 | 沿用现状不支持；前端 `sending` 已串行化，runtime 按 session_id 覆盖 |
| 同一文档并发导入 | 沿用现状不支持（同名覆盖互踩）；中止回退按 `task_id` + 标题，可能与并发任务互相影响，需避免同时导入同名文档 |
| 本地文件名并发冲突 | 同名上传本就互相覆盖；回退删本地文件前用 `path_in_use` 跳过被占用路径 |
| 在途上传晚于第一遍回退 | 间隔 1.5s 的第二遍兜底；更慢的极端情况可能留孤儿图片目录，下次同名导入收尾会清掉 |
| 中止时另一个分支正在写区 | 等 `writes_in_flight` 归零（≤10s）后再回退，避免写回残留 |
| 失败（异常，非中止） | 保持现状：不回退，日志留痕；新建型可能留孤儿图片目录，下次同名导入收尾会清掉 |
| 多 worker 部署 | runtime 与进度状态一样是进程内的，需要单 worker；多 worker 化不在本 Phase |
| MinerU 远端任务 | 无法取消远端解析，中止只是停止轮询，不再下载/写库 |

## 10. 备选方案与被否决项

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| `asyncio.Task.cancel()` 强杀 | 否决 | LangGraph 同步节点在线程里，取消只影响等待方，线程继续跑，可能「回退后又被写回」 |
| 前端只停止渲染 / 断开 SSE | 否决 | 后端继续生成并写库，是假中止 |
| 中止时按 `file_title` 删 Milvus 行 + 制品 | 否决 | 同名覆盖会误删旧文档；zip 多分支也会误伤其它标题 |
| 无条件允许中止并回退已写入数据 | 部分采纳 | 新建型写区可回退；覆盖型一旦开始就拒绝，因为旧文档已删，回退后旧新皆失 |
| 三份制品也做 staging（路径带 task_id） | 暂不做 | 可让覆盖型也可全程中止，但改动 V1-7 路径约定、URL 变化、需清理旧任务目录；P2 用「覆盖动作前中止 + 新建型可回退」达到同等安全性，成本更低，留作后续强化 |
| 把写区前移到图片上传之前 | 等价于整体不可中止 | 会把图片识别/切分等长耗时阶段都变成不可中止，违背需求 |

> 如果后续要做「全程可中止」，升级路径是：三份制品改为 `<dir>/<file_title>/<task_id>/…`，新行先插入、旧行在收尾时按标题删除非当前任务目录；届时写区可以缩到毫秒级、甚至取消。P2 不引入该改动。

## 13. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 写区重排引入同名覆盖回归 | 单独回归「同名覆盖成功导入」「zip 多分支」；写区顺序与现状一致，只前移纯计算 |
| 图片路径变化影响旧文档 | 旧文档 URL 不带 task 段，仍可读；删除接口清整棵标题目录；上线前用旧文档验详情/删除 |
| 前端口径分叉（query 用 `cancelled`、import SSE 的 `complete`） | 统一用 `cancelled`；import 的 `complete` 映射保持现状，新增分支只处理 `cancelled` |
| 在途调用导致「停止按钮迟钝」 | UI 中止中态 + 明确文档；流式阶段逐 chunk，体验最好；MinerU 轮询 0.2s 分片；模型调用受超时约束 |
| 中止与完成竞态 | 查询不做 graph 后置取消检查（final 在 graph 内）；导入补 `import-after-graph`（完成事件由 service 推）；HTTP 只表示受理 |
| 单 worker 前提 | 与现有 `task_utils` 一致；文档标注；多 worker 化另行立项 |
| 回退失败 | 逐步 try/except 收集 errors；任务仍置 cancelled；`rollback_ok=false` 让前端提示，服务端日志留痕 |

## 附：中止机制调研事实（2026-10-25）

> 以下来自本仓库 LangGraph 1.2.12 + 最小同步图实测，供下一次调研/定稿参考，不构成 P2 实现依据。

1. **同步节点无法安全取消**：给同步节点配 timeout 在 `compile()` 阶段即报
   `ValueError: Node timeouts are only supported for async nodes because sync Python execution cannot be safely cancelled in-process.`
2. **`asyncio.Task.cancel()` 不等于停止**：一个分支取消后 `ainvoke` 立即返回，其它同步分支的线程继续跑完；没有 checkpointer 时拿不到任何图状态。
3. **有 checkpointer 时可取证**：取消后 `aget_state(config)` 返回最后完成超步的 `values`、`next`（被打断节点）、`tasks[].error`（`CancelledError` 的字符串形式）；3.5s 后在途线程结束，快照不变。
4. **resume 是重跑**：`ainvoke(None, config)` 会重新执行被打断的节点（实测又跑了一次 3s 节点），属于 at-least-once，副作用可能重复。
5. **无 checkpointer**：`aget_state` 直接 `ValueError: No checkpointer set`；只能用自有 run registry / `astream` 保留的快照。
6. **fan-out**：取消后 `next` 会出现重复分支名（如 `('branch','branch','branch')`），`tasks` 多个 `CancelledError`；整步未完成时 `values` 不更新。
7. **`astream` 关闭** 与 task cancel 等价，状态停在同一超步；checkpointer 只解决“事后状态”，**不解决 Milvus/MinIO 副作用回退**。
