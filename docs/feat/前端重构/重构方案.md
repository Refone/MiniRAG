## 0. 方案概要

| 问题（PRD） | 本方案的核心动作 |
| --- | --- |
| 结构不清晰：逻辑杂糅在两个 page 中 | 把 ChatPage（370 行）/ ImportPage（747 行）中的内联组件逐一提炼为 props 化组件，页面退化为"组合层"（目标 ≤ 250 行/页） |

| 相似组件并存 | 合并 4 组高相似逻辑：三枚状态图标 → `StatusIcon`；ChatPage 进度区与导入任务日志 → `StatusLog`；两处空态 → `EmptyState`；删除弹窗 → `ConfirmModal`（容忍细微视觉差异） |

**总原则**：单向依赖（pages → components → hooks/utils/types；pages → store；store → lib；**dev → src，src 不依赖 dev**）；每阶段结束 `npm run build` 必须绿；组件一律 props 化、禁止直接 import store（这是画廊可独立挂载的前提）；**`web/src` 只放业务代码，一切开发工具/调试页/临时文件进 `web/dev/`**（反馈 01）。

## 2. 设计原则与决策记录

1. **不引入 react-router**。`<Activity>` 双保活是 Session-MVVM 的核心机制（切页不卸载、SSE 不断流）；react-router 会卸载页面直接破坏它。App.tsx 内 `PageKey` 状态切换即本项目的"路由"，**维持 `"chat" | "import"` 两页不变**。
2. **store 按存储方式分层**：localStorage 持久化（`preferenceStore`，zustand persist）与纯内存会话态（`chatStore` / `docsStore`，不再各自 persist）物理分离；主题状态从 React Context 迁入 preferenceStore，消灭第三套手写 localStorage。
3. **组件契约**：所有 `components/` 组件 props 化、受控优先、不 import 任何 store；数据由 page 接线。这同时是画廊可独立挂载、可喂 fake 数据的结构保证。
4. **CSS 保持全局类名体系**，只做按域拆文件 + 死代码清理，不迁移 CSS Modules / 原子化方案（本次目标是结构治理，不是样式体系改造，避免大规模视觉回归风险）。
5. **常量集中规则**：跨模块共享 → `lib/constants.ts`；模块私有 → 就近保留（如 imageCache 的容量上限）。
6. **合并宽容度**（PRD 要求 1）：逻辑高度类似即合并为单一组件，容忍细微 UI 差异，差异通过 props（`summary`、`className`、`kind` 等）表达。
7. **粒度守则**（PRD 要求 2/3）：页面 ≤ ~250 行、组件单文件 ≤ ~200 行、store ≤ ~300 行为参考上限；只做"职责单一 + 内聚"的切分，不为拆而拆。
8. **旧缓存不迁移、直接清理**（反馈 01）：preferenceStore 以全新 `kb-preferences` key 从默认值起步，**不读旧数据**；废弃的旧 key（`kb_theme` / `kb-chat-store` / `kb-docs-store`）由 `web/dev/clean_cache.py` 一键清理。旧 key 与新 key 互不干扰，不清理也不影响新版本功能，清理是卫生动作。
9. **画廊与开发工具独立于业务代码**（反馈 01）：components-gallery 做成 `web/dev/components-gallery.html` 独立页面（Vite dev server 直接访问，`@/` 别名照常可用），画廊代码、fake 数据、样式、清理脚本全部放 `web/dev/`；App/NavBar/PageKey **不加** gallery 页。
10. **src 纯净原则**（反馈 01）：`web/src` 只放业务代码；任何开发工具、调试页、临时文件一律进 `web/dev/`，目录依赖方向允许 dev → src（复用业务组件与样式），禁止 src → dev。

## 4. 分域重构细节

### 4.1 types/ —— 类型契约集中

- `lib/types.ts` 按域拆为 `types/app.ts` / `types/chat.ts` / `types/docs.ts`。
- `lib/api.ts` 中的接口定义（`DocsListItem`、`DocsDetailResponse`、`DocsChunkItem`、`DocsListResponse`、`DocsDeleteResponse`、`QueryPayload`、`ImportUploadResponse`）全部迁入对应域文件——API 模块只留函数，不留契约。
- `ProgressView` / `StatusResponse` 被 chat 与 docs 双域引用，放 `types/app.ts`（跨域共享层）。
- `PageKey` 维持 `"chat" | "import"` 不变（画廊是独立 dev 页面，不属于应用路由）。
- 各目录下不放 index barrel（文件少、粒度适中，避免桶文件带来的循环依赖风险）。

### 4.2 utils/ —— 纯函数

- `chatUtils.ts`（236 行，混合时间/文本/Markdown 三类职责）拆为：
  - `utils/time.ts`：`nowTime` / `formatTime`
  - `utils/text.ts`：零宽字符剥离、URL 清洗/提取/去重、图片 URL 判定
  - `utils/markdown.ts`：Markdown 链接目标修复（BUG-005/007 防御逻辑）、流式未闭合图片截流（BUG-006 相关）、历史消息图片解析；并吸收 ImportPage 内的 `stripInlineMarkdown`
- `utils/id.ts`：`makeId`（chatStore 与 docsStore 双份造 id 收敛为一）
- `parseEventData` 收敛进 `lib/sse.ts`（见 4.4），消除双份。

### 4.3 hooks/ —— 共享 Hook

| Hook | 来源 | 说明 |
| --- | --- | --- |
| `useScrollRestore` | `lib/scrollRestore.ts` | 原样平移（含 followBottom/resetKey 语义） |
| `useImageUrl` | `lib/imageCache.ts` | 拆出 Hook 部分；缓存核心留在 `lib/cache/imageCache.ts`（`getImageUrl` 同步读 + 订阅/`bump` 机制） |
| `useApiHealth` | ChatPage | 抽出 60s 轮询逻辑（interval 可配置），返回 `connected: boolean`；docs 页后续可复用 |

### 4.5 store/ —— 按存储方式分类

**分层依据 = 状态的存储/生命周期，而非功能模块**：

| 文件 | 存储方式 | 内容 |
| --- | --- | --- |
| `preferenceStore.ts` | localStorage（zustand persist） | `theme`、`enableWebSearch`、`enableHyde`、`previewMode` + `toggleTheme` 与三个 setter |
| `chatStore.ts` | 会话内存（不持久化） | `sessionId`、`messages`、`sending`、`historyLoaded`、`send/clearHistory/ensureHistoryLoaded`、模块级 `esRef` |
| `docsStore.ts` | 会话内存（不持久化） | `docs/total/refreshing/docsLoaded/selectedId/detail/detailLoading/files/toasts` + 全部动作、模块级 `esMap`/`refreshedTasks` |
| `sessionStore.ts` | 会话内存（预留） | 原样平移 |

**要点**：

1. **chatStore / docsStore 删除各自 persist 配置**，不再自带白名单持久化——"持久化"职责唯一归于 preferenceStore。
2. **theme 迁入 preferenceStore**：删除 `theme/ThemeContext.tsx`；App 内 `useEffect` 同步 `document.documentElement.dataset.theme`（zustand persist 同步水合，首帧无主题闪烁）；NavBar 改为 props 接收 `theme/onToggleTheme`。
3. **跨 store 动作**：`docsStore.switchMode` / `resetPreview` 内部调用 `usePreferenceStore.getState().setPreviewMode(...)`（getState 不在组件内调用，无 hooks 约束问题）。
4. **旧缓存不迁移**（反馈 01，决策 8）：

   旧 key 与新 key 互不干扰；旧数据由 `web/dev/clean_cache.py` 清理（见 §5.3），**不写任何迁移代码**。
5. **toast 留在 docsStore**（唯一使用方，避免为 30 行状态新建 store——粒度守则）；chat 未来需要 toast 时再拆 `uiStore`。

### 5.3 clean_cache.py —— 旧缓存清理脚本（反馈 01）

- **目标**：本轮**不写旧缓存迁移**（决策 8），由本脚本一键清理废弃的浏览器端旧数据。
- **清理对象**：`kb_theme`、`kb-chat-store`、`kb-docs-store`（与 `lib/constants.ts` 的 `LEGACY_STORAGE_KEYS` 同值清单，评审时对齐）；`kb_session_id` 保留（后端会话身份，默认不清，`--all` 才一并清除，清除后服务端历史对新会话不可见，慎用）。
- **实现方式**（Python 无法直接操作浏览器存储，故以"临时服务 + 浏览器执行"完成，无需业务代码配合）：

```python
# web/dev/clean_cache.py（示意）
LEGACY_KEYS = ["kb_theme", "kb-chat-store", "kb-docs-store"]   # --all 时追加 kb_session_id
# 1) http.server 起临时服务（127.0.0.1:5199），响应一个自包含 HTML：
#    内嵌 JS 按清单 removeItem，回显"清理前存在 / 已清理"明细与剩余 kb* key 列表
# 2) webbrowser.open("http://127.0.0.1:5199/") 自动打开执行
# 3) 页面提示清理完成后，Ctrl+C 退出脚本
```

- **用法**：`cd web/dev && python clean_cache.py`（或 `--all` 连会话身份一起清）。
- **说明**：旧 key 与新 `kb-preferences` 互不干扰，不清理也不影响新版本功能；清理属卫生动作，重构上线说明中引导用户执行一次即可。
