## 0. 结论摘要（TL;DR）

**根因**：两个页面的全部状态都存放在页面组件内部（`useState`），而 `App.tsx` 用条件渲染切换页面——切换即卸载、状态即丢弃；SSE（EventSource）在页面卸载时被主动关闭，processing 任务因此失联；图片没有任何前端缓存层，且后端 `/api/files` 未下发 `Cache-Control`，重挂后必然重新请求。

**推荐实现方式：分层 ViewModel 组合**（详见 §4）：

| 层                     | 选型                                                        | 职责                                                                                                                                              |
| ---------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 页面保活             | React 19 `<Activity>`（零依赖，已装 19.3.1）                | 保留滚动位置、输入草稿、预览模式、导入中间态等**视觉状态**                                                                                        |
| ② 会话全局 Store       | **Zustand v5**（约 1.1 kB gzip）                            | 页面状态 + **SSE 任务跟踪上移**（不再随页面隐藏/卸载断流）；预留 tokens、任务运行状态字段                                                         |
| ③ 请求缓存（前端内存） | V0 手写轻量 request-cache（并发去重 + TTL，约 50 行）       | 在浏览器内存里缓存 `/api/docs`、`/api/docs/{id}`、`/api/history` 的响应；TanStack Query 列为复杂化后备选；**不需要服务端缓存/Redis**（见 §2.3.2） |
| ④ 图片缓存             | 前端 session-global Blob 缓存 + 后端 `Cache-Control` 响应头 | 会话内图片零重复请求；HTTP 缓存兜底跨刷新                                                                                                         |
| ⑤ 持久化               | Zustand `persist` → localStorage（仅小状态）                | 开关、预览模式等跨刷新保留；大数据留内存                                                                                                          |

**两个关键设计结论**（由官方语义直接推出，详见 §2.1 / §4.3）：

1. `<Activity mode="hidden">` 会**销毁 children 的 effects（清理订阅）**。因此 EventSource 必须从页面组件上移到会话全局 Store，否则切 Tab 仍会断流——保活只能解决"视觉状态"，不能解决"任务跟踪"。
2. 图片缓存不能只靠浏览器 HTTP 缓存（后端现在没下发缓存头），需要"前端内存缓存 + 后端缓存头"两层配合。

### 1.2 PRD 状态清单归类

PRD 里要保存的数据，按"生命周期特征"可归为四类，这也是后面选型的依据：

| 类别                              | 状态项                                                                                                                               | 特征                                                                   |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| **A. 视觉/交互状态**              | 会话 cursor（滚动位置）、文档列表滚动、预览区滚动、预览区当前模式、导入页面状态（files 列表展示、view 切换、拖拽态）、输入草稿、开关 | 与 DOM 强绑定；切 Tab 需保留，刷新丢失可接受                           |
| **B. 任务跟踪状态**               | 查询任务（SSE 流式）、上传任务（SSE 进度）、processing 中的中间态                                                                    | **必须与页面生命周期解耦**（PRD 点名"丢失跟踪"最严重）；session global |
| **C. 服务端数据的前端缓存**       | `/api/docs/detail` 数据、文档列表、聊天历史、图片                                                                                    | 有失效语义（增删文档、导入完成）；会话内复用，刷新可重新拉取           |
| **D. 未来预留（session global）** | tokens 消耗、任务运行状态统一视图                                                                                                    | V0 只需在 Store 中留好挂载点，不实现                                   |

## 2. 候选方案分析

### 2.1 页面保活（解决 A 类 + 顺带缓解 C 类）

#### 方案 A1：React 19 `<Activity>`（官方，推荐）

React 19.2（2025-10）正式发布 `<Activity>`，本项目 19.3.1 可直接使用。官方语义（[react.dev/reference/react/Activity](https://react.dev/reference/react/Activity)）：

- `mode="hidden"`：子树以 `display: none` 隐藏；**其 Effects 被销毁、订阅被清理**；state 与 DOM 均保留；
- 隐藏期间子树仍会响应 props 更新重渲染，但**优先级低于可见内容**；
- 切回 `visible`：state/DOM 原样恢复，**Effects 重新创建**；
- 官方明确"概念上把 hidden Activity 视为已卸载"；`<StrictMode>` 会提前演练这种挂载/卸载。

对 PRD 的适配：

- ✅ 会话 cursor / 列表滚动 / 预览滚动 / 预览模式 / 导入中间态 / 输入草稿——**零代码保留**（DOM 不销毁，scrollTop、textarea 值都在）；
- ✅ 预览区图片、markdown 文档的 DOM 不销毁，已解码图片不重新下载；
- ⚠️ 隐藏时 effects 被销毁：ChatPage 的 60s 健康轮询、导入计时器等会暂停（恢复时重建，可接受甚至更省）；**但 SSE 会被 cleanup 关闭**（现有代码的卸载 cleanup 会执行）——所以 B 类必须上移到 Store（§4.3）；
- ⚠️ 隐藏树仍会低优先级重渲染：流式 delta 高频更新 messages 时，隐藏的 ChatPage 仍会被唤醒渲染（优先级低）。缓解方案见 §5-风险 R4；
- ⚠️ 边界：只渲染纯文本（无 DOM 元素）的子树在 hidden 时不产生任何输出——本项目两个页面根都是 `<div>`，不受影响；
- 优点：改动最小（只改 `App.tsx`）、零依赖、官方支持 Tab 场景；缺点：内存不释放（两个页面常驻），对当前两个轻页面可接受。

#### 方案 A2：CSS 保活（`display:none` / `hidden` 属性）

自己保留两个页面 DOM，切换时切换样式：

- ✅ 同样保留 A 类状态；**effects 继续运行**——SSE 不会断流（这是它与 Activity 的关键差异）；
- ❌ 代价：隐藏页所有后台开销全开（健康轮询、计时器、ResizeObserver、事件监听持续运行），随页面复杂度增长变成无谓负载；
- ❌ 需要自己管理"何时算隐藏"（页面组件需感知 visibility 才能暂停非必要工作），逻辑侵入页面；
- 结论：仅作为 Activity 出现意外限制时的**降级备选**，不作为首选。

#### 方案 A3：状态全提升 + 手工恢复（不用保活）

所有状态提到 Store，卸载重挂后从 Store 恢复，并手工记录/重放 scrollTop：

- ❌ 滚动位置、textarea 光标、`<details>` 展开态等**隐式 DOM 状态**要逐一手工序列化恢复，工作量大且永远追不完；
- ✅ 状态流最干净、内存占用最小；
- 结论：不推荐作为主方案；若未来引入真正路由（如 react-router）时再考虑（届时可配合 A1/A2 思想）。

### 2.2 全局状态库（解决 B 类 + Store 骨架）

| 方案                                          | 体积/依赖                    | SSE 适配                                                                                                                                                         | 评价                                                                 |
| --------------------------------------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **Zustand v5**                                | ~1.1 kB gzip，零传递依赖     | 组件外 `setState` 天然支持（SSE 回调在闭包里直接更新 store）；`persist` 中间件支持 localStorage/sessionStorage/自定义 storage + `partialize` + `version/migrate` | **推荐**：本项目场景的甜点位；官方文档齐全                           |
| 手写 external store（`useSyncExternalStore`） | 零依赖                       | 需自写 subscribe/getSnapshot，约 60-80 行                                                                                                                        | 可行。若团队坚决不引入依赖可作为替代；但持久化、选择器订阅要自己维护 |
| Redux Toolkit + RTK Query                     | 大（含 immer/redux ~30 kB+） | 支持，但样板多                                                                                                                                                   | 本项目状态规模完全用不上，杀鸡用牛刀                                 |
| Context + useReducer                          | 零依赖                       | 组件外更新需 ref 转发；**高频更新（流式 delta）会导致 Provider 下全树重渲染**                                                                                    | 不适合流式场景；适合低频主题类状态（项目里 ThemeContext 已用）       |

### 2.3 前端请求缓存：缓存服务端返回的数据（解决 C 类）

> 本方案是**前端内存缓存**——在浏览器里缓存后端响应，避免切 Tab 重复请求；

| 方案                              | 能力                                                                                                                     | 评价                                                                                                                                                                                 |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **手写 request-cache（V0 推荐）** | `Map<key, { data, ts }>` + 进行中 Promise 去重 + TTL/手动失效                                                            | 本项目只有 3 个读接口，50 行足够；失效规则简单（导入完成 → 列表失效；删除 → 列表+详情失效；清历史 → 历史失效）                                                                       |
| TanStack Query v5                 | queryKey 缓存、并发去重、`staleTime`/`gcTime`、后台重取、`persistQueryClient`（localStorage/IndexedDB 持久化）、DevTools | 能力全面且成熟；但引入一套"查询生命周期"心智模型与依赖。**列为备选**：当查询场景复杂化（分页、乐观更新、多端同步）时再迁移，V0 的 request-cache 接口形状可对齐 queryKey 以便日后切换 |

### 2.4 浏览器存储（逐项定位）

| 存储                        | 容量/特性                                                     | 本项目定位                                                                                                                                                              |
| --------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cookie                      | ~4 kB/条、随请求发送                                          | ❌ 不适合页面状态；仅后端鉴权可能用到                                                                                                                                   |
| localStorage                | ~5 MB/源、同步阻塞主线程、字符串、同源跨 Tab 共享、跨刷新持久 | ✅ **仅存小状态**：开关、previewMode、sessionId（已有）；❌ 不放大数据（detail.markdown_text 可达 MB 级，同步序列化会卡 UI，且撑爆配额）                                |
| sessionStorage              | 同上但每浏览器 Tab 独立、关 Tab 即清                          | ⚠️ 本次需求是应用内 Tab 切换，localStorage 已够用；sessionStorage 与"session global"语义更贴，但跨浏览器 Tab 不共享，价值有限，V0 不引入                                |
| IndexedDB                   | 异步、GB 级、支持 Blob/结构化克隆、跨刷新持久                 | 🔮 **V1 可选**：图片持久缓存、大文档离线缓存；V0 不引入（复杂度收益比不划算）                                                                                           |
| Cache API（`caches`）       | request/response 键值、可在无 Service Worker 时从 window 使用 | ⚠️ 对"图片 URL → Blob"可做 HTTP 层缓存，但与 IndexedDB 定位重叠、失效控制更繁琐；V0 用更简单的内存 Blob 缓存                                                            |
| 内存 Map（模块级/Store 内） | 最快、无序列化、**session global**（刷新即清）                | ✅ 图片缓存、request-cache 的载体，正合 PRD"session global"语义                                                                                                         |
| HTTP 缓存                   | 由响应头控制（`Cache-Control`/`ETag`）                        | ✅ 作为内存缓存失效后的兜底：后端给 `/api/files` 加缓存头（对象不可变，可激进 `max-age + immutable`），刷新后图片也无需重新拉取。**这是后端一行改动、收益明确的配套项** |

### 2.5 范围澄清：不是"跨浏览器 Tab"

PRD 的"跨 Tab"指**应用内导航 Tab**（对话 ⇄ 文档管理）。跨浏览器 Tab/窗口同步（BroadcastChannel、SharedWorker、Web Locks）不在本需求内；若未来需要（如多窗口任务进度同步），Store 的 `persist`/订阅结构可直接挂 BroadcastChannel 适配器，框架已预留。

## 4. 推荐方案（分层 ViewModel）

### 4.1 总体架构

```
App.tsx（page 状态 + <Activity> 保活两个页面）
 │
 ├─ <Activity mode>── ChatPage ──┐
 │                               │ useChatStore / useDocsStore 订阅
 ├─ <Activity mode>── ImportPage ┘
 │
 └─ 会话全局层（不随页面隐藏/卸载销毁）
     ├─ stores/chatStore.ts      # messages、sessionId、开关、sending、SSE(查询任务)
     ├─ stores/docsStore.ts      # docs 列表、selectedId、previewMode、files(导入)、SSE(上传任务)
     ├─ stores/sessionStore.ts   # 【预留】tokens 消耗、任务运行状态统一视图
     ├─ lib/requestCache.ts      # 通用请求缓存（并发去重 + TTL + 手动失效）
     └─ lib/imageCache.ts        # session-global Blob URL 缓存（LRU）
```

### 4.2 PRD 状态清单 → 落点映射

> 本节为选型层面的概览；**明细级落点**（每项缓存了什么、落到哪个文件哪个变量、用什么机制、关键代码位置）见 [方案设计-V0.md §4.5](./方案设计-V0.md)。

| PRD 状态项                           | 落点                                    | 机制                                       | 跨刷新                                    |
| ------------------------------------ | --------------------------------------- | ------------------------------------------ | ----------------------------------------- |
| 会话 cursor（滚动位置）              | ① Activity 保活                         | DOM scrollTop 不销毁                       | ✗（可接受）                               |
| 会话分页 cursor（未来分页化）        | ② chatStore 预留字段                    | —                                          | 可选 persist                              |
| 图片缓存（session global）           | ④ imageCache（内存）+ HTTP 缓存头       | fetch→blob→objectURL，LRU                  | ✗ 内存层；HTTP 头兜底 ✓                   |
| 文档列表 cursor（滚动）              | ① Activity 保活                         | DOM scrollTop 不销毁                       | ✗                                         |
| 文档列表分页 cursor（未来）          | ② docsStore 预留字段                    | —                                          | 可选 persist                              |
| 导入页面状态（view/files 展示/拖拽） | ① 保活 + ② docsStore（files 数组）      | 展示态保活；数据态入 Store                 | files 不持久（上传中断即作废，可接受）    |
| 预览区当前模式                       | ① 保活 + ② docsStore                    | 推荐同时入 Store + persist（localStorage） | ✓                                         |
| 预览区 cursor（滚动）                | ① Activity 保活                         | DOM scrollTop 不销毁                       | ✗                                         |
| 预览区图片缓存                       | ④ 同图片缓存层                          | 同上                                       | 同左                                      |
| `/api/docs/detail` 数据              | ③ requestCache（key=`detail:{doc_id}`） | 切回不重拉；删除/导入时失效                | ✗（刷新重拉可接受）                       |
| 聊天历史 / 文档列表                  | ③ requestCache + ② Store 快照           | 初始化一次，手动刷新/失效                  | ✗                                         |
| **processing 任务跟踪**              | ② Store 持有 EventSource                | **连接生命周期=会话，不=页面**             | 刷新后按 sessionId/taskId 重连（V0 可选） |
| tokens 消耗（预留）                  | ② sessionStore 字段                     | V0 仅留字段                                | persist 预留                              |
| 任务运行状态（预留）                 | ② sessionStore 统一视图                 | V0 由 chat/docs store 的 SSE 状态顺带提供  | —                                         |

### 4.3 关键设计点

**D1. SSE 上移（核心）**：把 ChatPage 的 `esRef`/`startSse` 逻辑与 ImportPage 的 `esRef: Record<fileId, EventSource>` 迁入对应 Store：

- `chatStore.send(query)`：发起 `/api/query` → 建 EventSource → progress/delta/final/`__close__`/error 回调内 `set()` 更新 store；页面只订阅展示；
- `docsStore.upload(file)`：同上，任务完成回调里触发列表刷新（现有 `refreshedTasksRef` 去重逻辑平移）；
- 收益：切 Tab 不断流（满足 PRD 最痛点）；刷新页面后仍可基于 `kb_session_id`/`task_id` 重连补进度（V0 可选，V1 必做）；
- 注意 StrictMode 双挂载：连接创建收敛到 Store 内幂等函数（同一 sessionId/taskId 复用已有 EventSource）。

**D2. 图片缓存**：

- 前端：`imageCache.ts` 提供 `getImageUrl(url): string`——首次 `fetch(url)` → `blob` → `URL.createObjectURL` 存入 Map，后续直接命中；仅对**同源 `/api/files/**`** 与允许 CORS 的外部 URL 生效（无 CORS 的外部图片无法 fetch，回退裸 URL + 依赖 HTTP 缓存）；LRU 上限（如 200 条 / 200 MB）防内存膨胀；`MarkdownContent`的`img`组件改为走`getImageUrl`；
- 后端：`/api/files` 响应加 `Cache-Control: public, max-age=86400, immutable`（MinIO 对象内容不可变，按目录前缀放行后安全），刷新后浏览器直接用 HTTP 缓存，不再打到 MinIO。

**D3. 持久化策略**：Zustand `persist` + `partialize` 只持久化小状态（`previewMode`、搜索开关、sessionId）；`messages`、`detail`、`files` 不持久化（刷新后由历史接口/请求缓存重建）。启用 `version` 字段，V1 加字段走 `migrate`。

**D4. 隐藏树的低优先级重渲染**：SSE 流式 delta 高频更新 store 时，隐藏中的 ChatPage 订阅者仍会被低优先级唤醒。V0 先接受（两页面规模小）；如流式高频更新实测卡顿，把"流式文本"从全局 store 改为"可见时才订阅"（`useChatStore(selector)` 在页面隐藏时跳过订阅，消息最终态由 store 兜底）——此优化点记入 §5 R4。

## 5. 风险与遗留问题

| #   | 风险                      | 说明 / 缓解                                                                                                    |
| --- | ------------------------- | -------------------------------------------------------------------------------------------------------------- |
| R1  | Activity 隐藏销毁 effects | 既有行为（官方语义），SSE/轮询上移后反成优点；页面内剩余 effects 需确保有正确 cleanup（StrictMode 已提前演练） |
| R2  | 图片 Blob 内存膨胀        | LRU 上限 + `revokeObjectURL` 淘汰；仅缓存同源/CORS 可用 URL                                                    |
| R3  | request-cache 失效遗漏    | 失效点收敛在 3 处（导入完成、删除、清历史），Store 动作内统一调用 cache.invalidate                             |
| R4  | 隐藏树低优先级重渲染开销  | 见 D4，V0 观测、必要时订阅裁剪                                                                                 |
| R5  | persist 版本演进          | 引入 `version`+`migrate`，避免 V1 加字段时丢状态                                                               |
| R6  | 刷新后任务断档            | V0 明确"刷新不保证恢复流式进度"；重连机制列 V1（配合未来任务运行状态）                                         |
| R7  | 外部图片 URL 无法前端缓存 | 受第三方 CORS/缓存头控制，只能依赖 HTTP 缓存与浏览器自有缓存，属已知边界                                       |

## 6. V0 落地步骤草案

1. **保活**：`App.tsx` 引入 `<Activity>`，两页常驻（改 2 行，立即缓解 A 类痛点）；
2. **基础设施**：`npm i zustand`；新增 `web/src/stores/`、`web/src/lib/requestCache.ts`、`web/src/lib/imageCache.ts`；
3. **ChatPage 迁移**：messages/开关/发送逻辑/SSE 入 `chatStore`；页面改订阅（`loadHistory` 移入 store 初始化，切 Tab 不再重拉）；
4. **ImportPage 迁移**：docs 列表/detail/预览模式/上传任务+SSE 入 `docsStore`；`selectDoc` 走 requestCache；
5. **图片缓存**：`MarkdownContent` img 走 `imageCache`；后端 `/api/files` 加 `Cache-Control`（1 行）；
6. **持久化**：persist 小状态 + version；
7. **验收**：按 PRD 场景逐条走查（切 Tab 图片不重拉、会话不跳尾、文档页右侧不丢、processing 任务切走仍可见进度）。
