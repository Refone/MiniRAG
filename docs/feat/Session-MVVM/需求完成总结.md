## 1. 需求概述

两个 Tab（会话页 / 文档管理页）切换即整体重渲染：滚动位置、预览模式、导入中间态、输入草稿全部丢失；图片重新请求；会话跳回末尾；文档页右侧回到缺省页；最严重的是 processing 任务（查询流式、上传进度）切走即在前端失联。需要一个类似 "ViewModel" 的机制管理页面状态与网络数据缓存（图片、文档详情等），并预留 tokens 消耗、统一任务运行状态的 session-global 挂载点。

## 2. 评审过程与决策记录

### 2.1 技术调研（`方案调研-V0.md` 定稿）

- **页面保活**：React 19 `<Activity>`（方案 A1，推荐）——隐藏即 `display:none`、state/DOM 保留、effects 销毁重建；A2 CSS 保活为降级备选，A3 状态全提升不推荐；
- **全局状态库**：**Zustand v5**（~1.1 kB，组件外 `setState` 天然适配 SSE；备选：手写 external store / Redux Toolkit / Context+useReducer）；
- **请求缓存**：V0 手写轻量 request-cache（并发去重 + TTL，约 50 行）；TanStack Query 列为复杂化后备选；
- **图片缓存**：前端 session-global Blob 缓存 + 后端 `Cache-Control` 响应头双保险；
- **持久化**：Zustand `persist` → localStorage，只存小而稳定的 UI 偏好；
- **两个关键设计结论**：① `<Activity mode="hidden">` 会销毁 children effects → **EventSource 必须上移到会话全局 Store**，否则切 Tab 仍断流（保活只救"视觉状态"，救不了"任务跟踪"）；② 图片缓存不能只靠 HTTP 缓存（后端原未下发缓存头），需前后端配合。

### 2.2 方案设计评审（`方案设计-V0.md` 定稿）

- 四条架构调整原则：**A1** 页面从"数据源"变"视图"；**A2** SSE 生命周期绑定会话不绑定页面；**A3** 保活与上移双轨分工；**A4** HTTP 与缓存分层收敛（api.ts / requestCache / imageCache / persist）；
- 状态落点明细（§4.5）：复用载体只有四种——① 浏览器内存 ② localStorage ③ HTTP 缓存 ④ 页面 DOM（保活），**不引入任何数据库（含 Redis）**；
- 风险 R1–R7 全部有处置对照（§7）。

## 3. 最终方案要点

```
App.tsx（page 状态 + <Activity> 双保活）
 ├─ <Activity mode>── ChatPage ──┐
 │                               │ 订阅
 ├─ <Activity mode>── ImportPage ┘
 └─ 会话全局层（不随页面隐藏/卸载销毁）
     stores/chatStore      消息 + 查询 SSE（模块级 esRef）
     stores/docsStore      列表/详情/上传任务 + 上传 SSE（esMap）
     stores/sessionStore   【预留】tokens / 任务状态（V0 仅骨架）
     lib/requestCache      响应缓存（并发去重 + TTL + 前缀失效）
     lib/imageCache        图片 Blob 缓存（封顶跳过、不淘汰）
     lib/scrollRestore     滚动守卫（贴底跟随 + 内容身份键）
```

- **视觉状态**（滚动、草稿、左滑、拖拽）靠 Activity 保活零代码保留；**数据/任务状态**靠 store；页面只订阅渲染 + 保留纯视觉私有状态；
- **缓存 key**：`docs:list`（30s）/ `docs:detail:{docId}`（5min）/ `history:{sessionId}`（30s）；失效点收敛在 store 内 3 处动作（上传完成、删除、清历史）；
- **imageCache**：封顶 300 条 / 300MB、满后新图走原 URL、绝不淘汰（BUG-002 修正）；后端 `/api/files` 加 `Cache-Control: public, max-age=86400, immutable` 兜底跨刷新；
- **persist**：`kb-chat-store`（开关）+ `kb-docs-store`（previewMode），partialize 白名单，version 1；sessionId 沿用 `kb_session_id`。

> 经验沉淀：① 模型输出是**不可信输入**，前端渲染入口必须做伪影防御（零宽字符、畸形图链语法），并以存储层字节级证据定位根因；② `<Activity>` 隐藏销毁 effects 的官方语义贯穿全链路——SSE 上移 store、图标动画定格、滚动守卫、缓存"不淘汰"决策全部由此推导；③ 高频流式场景下，渲染层组件类型必须稳定（模块级定义）+ 订阅尽量无状态化，否则每个 delta 都会触发重挂载。
