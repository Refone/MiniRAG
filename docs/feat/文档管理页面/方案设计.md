# 文档管理页面 · 方案设计

> 状态：**草案 v0.1（待评审）**
>

## 1. 背景与目标

- 现状：`ImportPage` 只有「上传文件 + 轮询进度」能力，文档入库后无法浏览、校验、删除。
- 目标：把它升级为 **文档管理页面**——文档的添加（导入）、列表展示、预览（markdown / chunks）。
- 非目标（MVP 不含，记录备查）：列表搜索/过滤、批量操作、元数据编辑、分页、权限。

## 2. 需求评审定案（决策记录）

评审基于 `需求描述.md` + 现有代码（`milvus_client` / `minio_client` / 导入链路 / `web/`）。
以下为已与需求方确认的决策，作为后续设计与验收的依据：

| # | 决策点 | 结论 | 说明 |
| :-- | :-- | :-- | :-- |
| D1 | 上传时间 | **本版不显示** | `minirag_docs` 无时间字段，Milvus 不支持给已有 collection 加字段。列表以 `doc_id` 倒序近似「最近导入在前」（auto_id 自增单调）。后续需要再迁移补 `created_at` |
| D2 | 预览访问方式 | **后端代理接口** | 存储 URL 含 `minio:9000` 内网主机名且匿名 GET 无 CORS 头，浏览器不可直连/内嵌渲染。预览统一走 `GET /api/docs/{doc_id}/artifact`；markdown 内嵌图片 URL 由前端渲染时重写为代理路径 |
| D3 | chunks 展示 | **split 卡片视图** | 每 chunk 一张卡片：序号 + `title_stack` 面包屑 + 内容 + 字符数，风格对齐 `tools/markdown-splitter` |
| D4 | 删除交互 | **二次确认弹窗 + 失败 toast** | 破坏性操作防误触；级联删 Milvus docs/chunks + MinIO 制品，失败保留条目并报错 |
| D5 | 列表刷新 | **导入 complete 自动刷新 + 手动刷新按钮** | 自动刷新在后台发生；用户停留在导入视图时列表静默更新，切回即可见 |

随决策确定的实现口径：

- **原始文档类型**：无字段，从 `origin_file_url` 后缀推断（`.pdf` → pdf / `.md` → markdown / 其他或空 → unknown），由后端统一推断后随列表返回。
- **Chunks 数量**：无字段，列表接口用一次 `doc_id in [...]` 批量查询 `minirag_chunks` 后 Python 分组计数，避免 N+1。
- **排序**：`doc_id` 倒序（近似最近导入在前）。

## 3. 总体设计

### 3.1 布局

```
┌───────────────────────────────────────────────────────┐
│ NavBar（对话 · 文档管理【原名「文件导入」，标签与文案同步改】）│
├──────────────────┬────────────────────────────────────┤
│ 左半区（约 380px）│ 右半区（flex: 1）                   │
│ ┌──────────────┐ │ ┌────────────────────────────────┐ │
│ │ 📚 文档列表(4)│ │ │ 《选中文档标题》  [PDF/Markdown] │ │
│ │        🔄    │ │ ├────────────────────────────────┤ │
│ │ ┌──────────┐ │ │ │                                │ │
│ │ │ doc item │ │ │ │ markdown 预览 或 chunks 卡片    │ │
│ │ │ ·标题/类型│ │ │ │                                │ │
│ │ │ ·chunks数│ │ │ │ （初始空态：提示左侧选择文档）     │ │
│ │ │ ·关键词  │ │ │ │                                │ │
│ │ │ ▸摘要    │ │ │ │                                │ │
│ │ │ [删][Json]│ │ │ │                                │ │
│ │ └──────────┘ │ │ │                                │ │
│ └──────────────┘ │ └────────────────────────────────┘ │
│   [＋ 添加文档]   │   [ Markdown | Chunks ] 切换        │
└──────────────────┴────────────────────────────────────┘
```

### 3.2 左半区两视图（卷帘门）

左半区是上下两层叠放的视图容器（`overflow: hidden`）：

- **列表视图在上层**（z 轴更高）：文档列表 + 底部「＋ 添加文档」按钮。
- **导入视图在下层**：与原 ImportPage 一致（上传区 + 任务进度列表），顶部为「← 文档列表」返回按钮。
- 点击「添加文档」：列表视图 `translateY(-100%)` 上升收起（卷帘门收起），露出下层导入区；
  点击「文档列表」：列表视图下降复位。过渡 ~400ms，ease-in-out。
- 导入视图常驻（不做卸载），切回列表时上传轮询不受影响。

### 3.3 核心交互流程

- **选择预览**：点击 item 非按钮区域 → 右半区加载该文档 markdown（fetch 代理接口，有骨架屏/加载态）；切换文档时取消/忽略过期请求。
- **删除**：弹确认框（提示级联删除不可恢复）→ `DELETE /api/docs/{doc_id}` → 成功移除条目 + toast；若删的是当前选中文档，右半区回空态。
- **预览切换**：右半区底部 `[Markdown | Chunks]` 一对按钮，切换渲染模式；按 (doc_id, mode) 缓存已拉取内容。
- **导入完成**：任一上传任务 complete → 后台自动刷新列表（D5），不强制把用户从导入视图切回列表。

## 4. 后端设计

### 4.1 路由前缀统一 `/api`（修复现有不一致，前置项）

现状问题（评审时发现）：nginx 把 `/api/*` 原样转发给 FastAPI，但 FastAPI 路由没有 `/api`
前缀；prod 前端 `API_BASE = origin` 直调 `/upload` 命中 SPA 回退；后端健康检查探
`/api/health` 同样 404。即 **docker 部署下 API 链路当前不通**，新增接口会撞上同一问题。

方案（改动最小、dev/prod 统一）：

1. FastAPI 建 `APIRouter(prefix="/api")`，现有全部路由（health / upload / upload/status /
   query / query/sse / history）+ 新增路由迁入 → 实际路径全部变为 `/api/...`。
2. nginx 配置**不动**（保留 URI 转发，正好匹配）；`web-backend.yaml` 健康检查 URL 变正确，也**不动**。
3. 前端 `resolveApiBase()` 返回统一追加 `/api`：dev = `http://127.0.0.1:8000/api`，
   prod = `{origin}/api`。ChatPage / 新页面所有请求自动适配。
4. Vite dev 的 `/api` 代理保留（当前前端走绝对地址直连 8000，代理暂未启用；保留以备将来切相对路径）。

### 4.2 新增接口契约

#### 4.2.1 `GET /api/docs` — 文档列表

```jsonc
// 200
{
  "status": "ok",
  "docs": [
    {
      "doc_id": 469734951640943804,   // minirag_docs 主键，也是 chunks 的 doc_id
      "file_title": "华为擎云 S520 Gen2 用户指南-(YTGZ,Windows11_03,zh-cn)",
      "file_type": "pdf",             // pdf | markdown | unknown（后端推断）
      "chunk_count": 12,              // 后端批量统计
      "docs_keywords": "擎云, S520, 用户指南",
      "docs_abstract": "……",
      "origin_file_url": "http://minio:9000/minirag/origin-files/...",
      "final_markdown_url": "http://minio:9000/minirag/final-markdowns/...",
      "chunks_url": "http://minio:9000/minirag/chunks-json/..."
    }
  ]
}
```

- 排序：`doc_id` 倒序。不返回向量字段。空库返回 `docs: []`。
- 实现：`query` docs 全标量字段（`limit=16384`，MVP 不分页）→ `query` chunks
  `filter="doc_id in [...]"` 只取 `doc_id` 列 → Python 分组计数。

#### 4.2.2 `GET /api/docs/{doc_id}/artifact?kind=origin|markdown|chunks|image&name={文件名}` — 预览代理

| kind | 返回 | Content-Type | 用途 |
| :-- | :-- | :-- | :-- |
| `markdown` | final_markdown 内容 | `text/markdown; charset=utf-8` | 右半区渲染 |
| `chunks` | chunks.json | `application/json` | 右半区分段视图 |
| `origin` | 原始文档（PDF/md） | 透传对象头（`application/pdf` 等） | 「PDF」按钮新标签页预览 |
| `image` | markdown 内嵌图片 | 透传/推断 | markdown 渲染时 `<img>` 引用 |

- 对象定位：kind∈{markdown,chunks,origin} 时按 doc 行的对应 URL 解析出 object_name
  （剥掉 `scheme://endpoint/{bucket}/` 前缀）；kind=image 时按
  `{image_dir}/{file_title}/{name}` 拼 object_name（`name` 仅取文件名，禁止路径穿越）。
- `Content-Disposition: inline; filename=...`（origin/chunks 便于新标签页展示）。
- 流式返回（`StreamingResponse` + `minio get_object` 的流），不整读进内存。
- 错误：doc 不存在 → 404；对象缺失/MinIO 异常 → 502，body 给出提示。

#### 4.2.3 `DELETE /api/docs/{doc_id}` — 删除文档

```jsonc
// 200  {"status": "ok", "msg": "已删除《标题》(docs/chunks/制品)"}
// 404  {"detail": "文档不存在: {doc_id}"}
// 500  {"detail": "删除失败: 已完成 X 步，失败于 Y（详见后端日志）"}
```

删除顺序（先摘索引、后清制品）：

1. `query_doc_row_by_id(doc_id)` 取回行（task_id / file_title）；无 → 404。
2. `delete_chunks_by_doc_ids([doc_id])` — **只按 doc_id 删**，不复用按 file_title 的兜底删除
   （避免不同 task_id 批次间 file_title 撞名时误删他行 chunks）。
3. `delete_docs_by_id(doc_id)`（新增辅助，现有只有按 file_title 的）。
4. `MINIO_CLIENT.clear_doc_artifacts(task_id, file_title)` 清该行自身 task_id 前缀的三份制品目录。

失败处理：任一步抛错 → 500 + 已完成的步骤说明；**不回滚**（避免半删索引更糟），
日志记录齐全，便于人工补齐（MinIO 清理幂等，重试安全）。

### 4.3 数据访问层新增

- `milvus_client.py`：`query_doc_row_by_id(doc_id)`（输出全标量字段）、`delete_docs_by_id(doc_id)`。
- `minio_client.py`：`get_object(object_name)`（返回流响应）、`url_to_object_name(url)`（剥桶前缀）。
- 文件类型推断放 `import_service` 或新 `docs_service`（`src/service/docs_service.py` 统一承载
  列表/删除/制品三件事，`api` 层只做编解码——沿用现有 api→service→processor 分层）。

### 4.4 markdown 内图片的代理重写

- 存储的 markdown 保持规范（图片 URL 指向 MinIO），**不改存储内容**。
- 前端渲染时把 `<img src>` 重写为
  `{API_BASE}/docs/{doc_id}/artifact?kind=image&name={encodeURIComponent(文件名)}`
  （文件名取原 URL 最后一段，`file_title` 由选中文档已知，后端按 4.2.2 定位对象）。
- 复用 `web/src/components/Markdown.tsx` 的 `MarkdownContent`，为其扩展一个可选
  `rewriteImgSrc` 钩子（chat 场景不传、文档预览场景传），图片"点击新标签页打开"沿用现有交互。

## 5. 前端设计

### 5.1 文件与组件拆分

```
web/src/pages/DocsPage.tsx            # 原 ImportPage.tsx 重命名；页面骨架：左区两视图 + 右区预览 + toast
web/src/pages/ImportPage.tsx          # 删除（内容拆分到下面两处）
web/src/components/docs/
  DocListPanel.tsx    # 列表视图：header(计数+刷新) + DocListItem 列表 + 底部「添加文档」
  DocListItem.tsx     # 单条：标题/类型徽标/chunks 数/关键词 chips/摘要(details 默认收起)/按钮组
  ImportPanel.tsx     # 导入视图：现 ImportPage 的上传区 + 任务进度列表（逻辑原样平移）
  PreviewPanel.tsx    # 右半区：header(标题+类型) + 内容区(markdown|chunks) + 底部模式切换
  ChunksView.tsx      # split 卡片视图（Chunk{content, level, title_stack} 解析自 chunks.json）
  ConfirmDialog.tsx   # 删除二次确认
  Toast.tsx           # 轻提示（成功/失败）
web/src/lib/api.ts    # 新增 DocsListItem / DeleteDocsResponse 类型与请求封装
web/src/components/Markdown.tsx  # 扩展可选 rewriteImgSrc 钩子（§4.4）
```

- `App.tsx` 渲染 `<DocsPage />`；`PageKey` 建议 `"import"` → `"docs"`（语义一致），
  `NavBar` 标签「文件导入」→「文档管理」、副标题文案同步。
- 上传轮询逻辑（`pollStatus` / 定时器清理 / 失败去重上报）从现 ImportPage 平移进
  `ImportPanel`，行为不变；`import` 完成回调新增一个 `onImportCompleted` 通知页面刷新列表（D5）。

### 5.2 状态与数据流

```
DocsPage state:
  view: "list" | "import"          # 卷帘门所在视图
  docs: DocsListItem[]             # 列表数据（loading/error 态独立字段）
  selectedId: number | null        # 选中文档
  previewMode: "markdown" | "chunks"
  previewCache: Map<`${docId}:${mode}`, string>   # 避免反复拉取
  toastList
```

- 列表刷新触发：页面挂载 / 手动刷新按钮 / 任一导入任务 complete 回调；请求去重（上一次未返回时忽略新的手动刷新）。
- 预览拉取：选中 → 骨架屏 → `GET artifact?kind=markdown`；切 chunks → 拉 `kind=chunks` 并客户端
  `JSON.parse` 为 `Chunk[]`；请求竞态用 docId 时间戳守卫丢弃过期响应。
- 删除成功后：`docs` 移除 + 若为 `selectedId` 则置空并清缓存 + toast。

### 5.3 预览渲染

- **Markdown 模式**：`MarkdownContent`（react-markdown + GFM，安全不渲染原始 HTML）+
  `rewriteImgSrc` 代理重写（§4.4）。
- **Chunks 模式（split 卡片，D3）**：卡片头 = 序号徽标 + `title_stack` 非空项用 ` › ` 连接的面包屑；
  卡片体 = chunk 内容（pre-wrap 原文，不二次转 markdown）；卡片脚 = 字符数。逐卡渲染（非虚拟列表，
  大文档性能列入 §6 边界）。

### 5.4 卷帘门动画

- 左区容器 `position: relative; overflow: hidden`；两层视图 `position: absolute; inset: 0`。
- 列表视图 `z-index: 2; transform: translateY(0)`，导入态 `translateY(-100%)`；
  `transition: transform 0.4s cubic-bezier(0.33, 1, 0.68, 1)`。
- 两层都常驻挂载（导入区轮询不中断）；动画期间不触发滚动条跳动（外层 overflow hidden）。

### 5.5 交互细节

- 空库：列表区空态「文库为空，点击下方添加文档」；右区初始空态「在左侧选择一篇文档」。
- 加载态：列表骨架屏 / 预览骨架屏；错误态：面板内错误文案 + 重试按钮。
- 关键词展示为 chips（逗号拆分）；摘要 `<details>` 默认收起。
- 类型徽标：PDF（红）/ Markdown（蓝）/ unknown（灰）。
- 删除确认弹窗文案含「删除后将从 Milvus 与 MinIO 移除，不可恢复」。

## 6. 边界与异常

- **文档刚被删（预览竞态）**：artifact 404 → 预览区显示「文档已不存在」并自动从列表移除/刷新。
- **同名覆盖**：`file_title` 是导入覆盖键，同名重导入=整份替换，列表理论上一个标题一行；
  删除粒度为 `doc_id`（一行），不是文件标题。
- **zip 导入扇出**：一个 zip 产生多行文档，各自独立展示与删除（origin 为该分支的 md）。
- **大文档性能**：预览整文渲染 + 逐卡渲染 chunks，先接受；若卡顿后续引入
  「chunks 懒加载卡片 / 虚拟列表」迭代（记录备查）。
- **删除半途失败**：见 4.2.3，返回 500 + 步骤说明，前端 toast 提示稍后重试。
- **上传轮询与页面导航**：切到「对话」页时 DocsPage 卸载、轮询定时器清理（现有行为不变）；
  后端任务继续，返回页面后列表刷新可看到结果（上传中状态本身是前端内存态，不做跨页恢复）。
