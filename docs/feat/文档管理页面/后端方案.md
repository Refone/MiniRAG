# 后端方案（定稿）

> 本文是「文档管理页面」后端 API 的最终设计，已合并 [`后端评审反馈-v0.md`](./后端评审反馈-v0.md)（决策 V1-1 ~ V1-6）与 [`后端评审v1.md`](./后端评审v1.md)（V1-7）的全部结论。
> 存量数据按决策约定处理：库内均为测试数据，需求实现过程中可随意清库，不必考虑数据兼容与迁移。

## 1. 总体设计

### 1.1 端点总览（全部挂载 `/api` 前缀，V1-4）

| 端点 | 方法 | 职责 | 数据来源 |
| --- | --- | --- | --- |
| `/api/docs` | GET | 文档列表（分页） | Milvus `minirag_docs` |
| `/api/docs/{doc_id}` | GET | 文档详情（原文 / 切块 / 特征） | Milvus `minirag_docs` + MinIO |
| `/api/docs/{doc_id}` | DELETE | 删除文档及级联数据 | Milvus + MinIO |
| `/api/files/{object_name}` | GET | 资源代理：流式返回 MinIO 对象 | MinIO |

存量端点一并加 `/api` 前缀（V1-4）：`/api/upload`、`/api/upload/sse/{task_id}`（导入进度 SSE 推流，取代原轮询 `/api/upload/status/{task_id}`）、`/api/query`、`/api/query/sse/{session_id}`、`/api/history/{session_id}`、`/api/health`。

### 1.2 基本原则

- **链接代理入库**（V1-1）：所有入库 URL 均为相对代理路径 `/api/files/<对象名>`，运行时零改写；浏览器经前端同源入口访问（dev 走 vite `/api` 代理，prod 走 nginx `/api/` 反代）。
- **`doc_id` 全程字符串**：`minirag_docs.id` 是 Milvus auto_id（INT64，如 `469734951640943804`），超过 JS `Number.MAX_SAFE_INTEGER`（2^53−1），所有接口中 `doc_id` 一律以 JSON string 传输（后端 `str(id)`）。
- **错误响应**：统一 FastAPI 风格 `{"detail": "..."}`。
- **路由前缀对齐**：后端全部路由统一挂 `/api`；`web/nginx.conf` 现有 `location /api/ { proxy_pass http://backend:8000; }` 原样透传 URI，后端挂前缀后即正确匹配（无需改 nginx）；docker healthcheck 探的 `/api/health` 同步成立。

## 2. 资源代理与链接方案（V1-1 落定）

### 2.1 决策答复要旨

- **MinIO 端口问题**：9000 端口在 `docker/data-services.yaml` 已对外发布，但「存储地址」与「浏览器地址」的差异是**主机名视角**问题（容器内后端只能连 `minio:9000`，浏览器无法解析该域名）。代理方案让浏览器永远只访问前端同源入口，MinIO 无需进入前端视野，即「合二为一」。
- **代理地址入库**：资源代理接口 + 入库时把链接直接写成代理地址，markdown / 切块内容里的 URL 天然就是代理地址，运行时零处理。

### 2.2 链接形态

- `minio_client.upload_file` 的返回值改为**相对代理路径**。对象路径统一遵循 `<dir>/<file_title>/<文件名>`（V1-7：移除 task_id 层级）：

  - 三份制品：`/api/files/<dir>/<file_title>/<文件名>`（dir ∈ `origin-files` / `final-markdowns` / `chunks-json`）
  - 图片：`/api/files/markdown-images/<file_title>/<文件名>`

- 存储形态：Milvus 三个字段 `origin_file_url` / `final_markdown_url` / `chunks_url` 与 final markdown 内嵌图片链接全部存上述相对路径（VARCHAR 存储无压力）。
- 前端消费：`<img>` 与 `window.open` 直接使用相对路径，浏览器相对当前页面 origin 解析，无需拼接 host。

### 2.3 GET /api/files/{object_name}

- **参数**：`object_name` 路径参数（含 `/`，FastAPI 使用 `:path` 转换器）。
- **行为**：`stat_object` 取 content_type → `get_object` 流式返回（`StreamingResponse`）；对象不存在 → 404。
- **用途**：PDF inline 预览（application/pdf）、chunks JSON 新标签打开（application/json）、markdown 内嵌图片渲染。
- **安全加固（默认开启）**：`object_name` 仅允许以下前缀之一，否则 404：`markdown-images/`、`origin-files/`、`final-markdowns/`、`chunks-json/`。
- **不改写**：该端点只做透传；detail 返回的 `markdown_text`、列表返回的链接均原样输出（无运行时替换）。

## 3. 通用约定

### 3.1 doc_id

- 传输：一律 string；
- 后端入参处理：`int(doc_id)` 转换，非法值直接 404。

### 3.2 文档类型 type 的推导

`minirag_docs` 没有类型列，按 `origin_file_url`（现为代理路径）的文件名后缀推导：

| origin_file_url 后缀 | type |
| --- | --- |
| `.pdf` | `pdf` |
| `.md` / `.markdown` | `markdown` |
| 空 / 未知 | `markdown`（final markdown 制品必然存在） |

markdown-zip 导入按 md 扇出，每篇文档的 origin 制品是单个 md 文件，因此列表 `type` 只会出现 `pdf` / `markdown`，与 demo-v4 的 `file_type` 一致。

### 3.3 keywords / abstract 返回格式（V1-6）

返回 Milvus 中入库时的原始字符串，后端不做拆分：`keywords`（逗号连接字符串）与 `abstract`（可为空）。前端按 `/[,，]/` 拆分 keywords 展示（与 demo-v4「特征」页一致）。

### 3.4 排序与分页

- 列表按 `id` 降序（新文档在前，与 demo-v4 一致）；
- 参数 `offset` + `limit`（默认 0 / 20，limit 校验范围 1~100）；
- `total` 通过 `count(*)` 查询获得。

### 3.5 created_at 字段（V1-2）

- `minirag_docs` 集合**新增 `created_at` 列**（INT64，epoch 毫秒），入库时写入；
- 本期**任何接口暂不返回**该字段（V1-3：列表 Item 以 demo-v4 为准），仅为未来「上传时间」展示预留；
- 说明：Milvus auto_id 雪花 ID 虽含时间信息，但不作为业务时间来源；
- 清库后集合由 `prepare_docs_collection` 重建，加列无迁移成本。

### 3.6 错误与删除语义（V1-5）

- `doc_id` 不存在：detail / delete 返回 **404** + `{"detail": "..."}`；
- 删除级联部分失败：记录 error 日志，返回 **500** + `{"success": false, "detail": "删除未完整完成: <原因>"}`，**不做自动补偿**（残留对象可在同名覆盖导入时被清理）。

## 4. GET /api/docs（列表）

### 请求

| 参数 | 位置 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `offset` | query | int | 0 | 跳过条数 |
| `limit` | query | int | 20 | 拉取条数（1~100） |

### 响应

```json
{
  "total": 6,
  "list": [
    {
      "doc_id": "469734951640943804",
      "title": "MiniRAG 架构设计文档",
      "type": "pdf",
      "pdf_link": "/api/files/origin-files/<file_title>/xx.pdf",
      "chunks_link": "/api/files/chunks-json/<file_title>/xx.json"
    }
  ]
}
```

- `doc_id`：string，Milvus 主键；
- `title`：`file_title`；
- `type`：推导规则见 3.2；
- `pdf_link`：`origin_file_url`（相对代理路径），仅 type=pdf 时非空，其余为 `null`（「PDF」按钮新标签页预览）；
- `chunks_link`：`chunks_url`（相对代理路径），「切块文件」按钮新标签页打开。

### 数据来源与查询要点

- 全部来自 `minirag_docs`；
- `output_fields` 仅取 `[id, file_title, origin_file_url, chunks_url]`，**不含** `abstract_dense_vector` / `keywords_sparse_vector` 向量列；
- 查询参数：`filter=""`、`order_by="id desc"`、`offset` / `limit`；
- 不返回 keywords / abstract / chunks 数量 / 上传时间（V1-3：列表 Item 以 demo-v4 为准）。

### 调用时机

1. 进入文档管理页面（首次）；
2. 点击「刷新」；
3. 导入任务完成后：前端经 `/api/upload/sse/{task_id}` SSE 推流收到 `complete` 时调用（demo-v4「导入完成 → 列表自动刷新」）；
4. 上传受理成功（POST /api/upload 返回 202）时**不**调用——文档尚未入库。

## 5. GET /api/docs/{doc_id}（详情）

### 请求

- `doc_id` 位于路径（string），无请求体。

### 响应

```json
{
  "title": "MiniRAG 架构设计文档",
  "markdown_text": "# ... 完整 markdown 原文（图片为相对代理路径）...",
  "chunks": [
    {
      "content": "...",
      "level": 3,
      "title_stack": [null, "h2", "h3"]
    }
  ],
  "keywords": "MiniRAG, 架构设计, 检索",
  "abstract": "记录 MiniRAG 系统的整体设计……"
}
```

- `title`：`file_title`；
- `markdown_text`：MinIO 中 final markdown 原文**原样返回**（内嵌图片已是相对代理路径，不做运行时改写）；
- `chunks`：与 chunks.json 原始结构一致 `{content, level, title_stack}`，顺序保持数组顺序。demo-v4 切块卡片依赖 `level`（H1/H2/top 徽标）；`chunk_size` 不返回（前端用 `content.length` 计算，ChunkRail 同源）；
- `keywords` / `abstract`：原始字符串（见 3.3）。

### 数据来源与查询要点

1. 按 `doc_id` 查 `minirag_docs` 行 → 取 `file_title / final_markdown_url / chunks_url / docs_keywords / docs_abstract`；行不存在返回 404；
2. 从 MinIO 读回 `final_markdown_url` 与 `chunks_url` 两个对象（按对象名定位），chunks 解析为 JSON 数组；
3. MinIO 对象缺失 → 404（数据不一致，视为文档不可用）。

### 调用时机

- 点击左列表 Item（非按钮区域）时调用；进入页面不调用，右区展示空态（demo-v4 v4 变更）。

## 6. DELETE /api/docs/{doc_id}

### 请求

- `doc_id` 位于路径（string），无请求体。

### 响应

- 成功：`{"success": true}`；
- `doc_id` 不存在：404（V1-5）；
- 级联部分失败：500 + `{"success": false, "detail": "..."}` + error 日志（V1-5）。

### 级联删除步骤（顺序）

1. 按 `doc_id` 查 `minirag_docs` 行，取 `file_title`；不存在 → 404；
2. 删除 MinIO 制品（V1-7 统一路径后全部按 `file_title` 定位，无需 task_id）：
   - 三份制品目录：`clear_doc_artifacts(file_title)`（origin / markdown / chunks）；
   - **图片目录**：`markdown-images/{file_title}`（需一并清理，否则成孤儿对象）；
3. 删除 `minirag_chunks`：`delete_chunks_by_doc_ids([doc_id])`；
4. 删除 `minirag_docs` 行：按 `id == doc_id` 精确删除。

> 删除顺序与同名覆盖流程（`node_document_embedding.step_2_delete_old_doc`）保持一致。

### 调用时机

- 用户点击 Item「删除」并在确认弹窗中确认后调用（demo-v4 删除确认弹窗）；成功后前端从本地列表移除该项（无需重新拉取列表）。

## 7. 数据模型与入库变更

### 7.1 minirag_docs 集合

- 新增列：`created_at` INT64（epoch 毫秒），见 3.5；
- 实现点：`MilvusDocsField.CREATED_AT`、`MilvusDocsItem.created_at`、`prepare_docs_collection` schema 加列。

### 7.2 入库链路

- `node_document_embedding.step_6_insert_docs_and_query_id`：写入 `created_at=int(time.time() * 1000)`；
- `minio_client.upload_file`：返回值由绝对 URL 改为相对代理路径 `/api/files/{object_name}`（见 2.2）。调用点 `node_md_img`（图片）与 `node_document_embedding`（三份制品）逻辑不变，仅返回形态变化；
- **对象路径统一（V1-7）**：
  - `doc_artifact_prefix(doc_dir, task_id, file_title)` 改为 `doc_artifact_prefix(doc_dir, file_title)`；
  - `clear_doc_artifacts(task_id, file_title)` 改为 `clear_doc_artifacts(file_title)`；
  - 清理 / 上传前缀统一带尾斜杠（`{dir}/{file_title}/`），避免 file_title 前缀相似的文件被误删；
  - `step_2_delete_old_doc` 中「按多个 task_id 前缀循环清理」的逻辑随之删除——单一前缀即覆盖该标题的全部历史制品，同名覆盖语义不变；
  - `task_id` 字段仍保留在 `minirag_docs` 表中（`query_doc_id` 兜底查询与任务溯源继续使用），仅从 MinIO 对象路径中移除。

## 11. 验收要点

1. 列表：按 `id` 降序、分页正确、`total` 准确、doc_id 为 string 且无精度丢失；
2. 详情：三模式数据齐全（原文渲染 / 切块含 level 与 title_stack / 特征含 keywords+abstract），图片可渲染；
3. PDF / chunks 新标签打开可用（相对代理路径经 vite / nginx 正确解析）；
4. 删除：Milvus docs / chunks 与 MinIO 三制品 + 图片目录无残留；重复删除返回 404；
5. 导入 complete 后列表自动刷新，受理成功（202）时不刷新；
6. 存量端点 `/api/upload`、`/api/query` 等全链路回归通过。
