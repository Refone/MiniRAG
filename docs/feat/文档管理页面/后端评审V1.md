# 后端评审 V1（待拍板决策项）

> 本文列出「文档管理页面」后端 API 设计中尚未确定、需要拍板的问题。
> 每个决策项包含：问题背景 / 可选方案 / 建议；请在各节末尾的「【决定】」后追加结论。
> 已确定的内容见 [`后端方案.md`](./后端方案.md)；全部决策落定后合并生成 `api-design.md`。

## 决策 1：MinIO 资源链接的浏览器可达性方案（最优先）

### 问题

`minirag_docs` 中存储的三个 url 与 final markdown 内嵌的图片链接，均由入库时的 `MINIO_ENDPOINT` 拼接（`minio_client.upload_file`）：

- 本地开发：`127.0.0.1:9000`，浏览器可达；
- Docker 部署：`docker/web-backend.yaml` 覆盖为 `minio:9000`，浏览器**不可达** → `pdf_link` / `chunks_link` 是死链，markdown 预览中图片裂图。

而 `后端评审v0.md` 的「特殊说明」声明：外网不可访问的资源在**入库阶段**处理、后端不做代理替换——但当前入库阶段并没有「公网可达地址」的配置，该声明目前是空的；demo-v4 的提示文案反而写的是代理端点 `GET /api/docs/{doc_id}/artifact?kind=...`，两者矛盾。

### 可选方案

**方案 A：入库阶段使用公网可达地址（推荐）**

- 新增配置 `MINIO_PUBLIC_ENDPOINT`（如 `http://127.0.0.1:9000` 或对外域名），`upload_file` / 图片上传用它拼接 URL 入库，存储仍走内网 `MINIO_ENDPOINT`。
- 优点：与「入库阶段处理、后端不代理」的原则一致；本地与 Docker 均正确；实现集中在 `minio_client`。
- 缺点：存量文档（含图片链接）仍是内网地址，需重导入或接受旧数据坏链。

**方案 B：后端提供代理端点**

- 新增 `/docs/{doc_id}/artifact?kind=origin|chunks|markdown` 等代理端点，detail 返回的 markdown 中图片链接改写为代理地址。
- 优点：浏览器只依赖后端域名，不暴露 MinIO。
- 缺点：推翻「后端不做代理替换」声明；每次预览 / 打开多一跳；图片链接改写是全文正则替换，实现与性能成本更高。

**方案 C：nginx 反代 MinIO**

- 在 `web/nginx.conf` 增加 `location /minio/` 反代到 minio 服务。
- 缺点：入库 URL 的 host 仍是 `minio:9000`，浏览器无法解析，需与「方案 A 的 URL 改造」叠加才有意义，单独使用收益有限。

### 建议

选 **方案 A**；同时明确存量文档的处理策略（重导入 / 接受坏链）。

### 【决定】

选择方案 A，存量文档不考虑，需求完成后会清库处理。

但是需要确定: 能不能把 Minio 当前端口直接设置为对外开放。
储存走内网，查询走外网，搞两个端口的意义是什么？不如合二为一。

其次，可不可以设计一个资源代理接口，直接在 Milvus 入库的时候，就把 Minio 链接替换为代理地址。
markdown 流式输出文档切片，含url的时候，输出的直接是代理地址，都不用做任何处理。

## 决策 2：「上传时间」字段的取舍

### 问题

PRD 要求列表 Item 显示「上传时间」，但 `minirag_docs` 集合没有任何时间字段（仅 id / task_id / file_title / 三个 url / keywords / abstract / 两个向量）。demo-v4 的最终 Item 只显示「标题 + 类型 + 三按钮」，不显示上传时间。

### 可选方案

**方案 A：废弃（推荐）**

- 以 demo-v4 为最终口径，列表不显示上传时间，后端不新增字段。
- 代价：PRD 该条需求需确认关闭。

**方案 B：新增时间字段**

- 在 `minirag_docs` 集合增加 `created_at`（如 INT64 毫秒时间戳或 VARCHAR），`node_document_embedding` 入库时写入；列表接口一并返回。
- 代价：Milvus 集合 schema 演进（加列）+ 存量数据补偿方案；若未来 Item 重新需要上传时间，这是必经之路。

### 建议

选 **方案 A**（短期）；若倾向长期可维护性，可接受方案 B 的迁移成本。

### 【决定】

已更新需求文档，当前不显示上传时间。
不过既然要清库，就顺遍改表结构，把上传时间字段加上，入库时写入，未来若需要显示上传时间即可直接使用。

## 决策 3：PRD 列表 Item 字段与 demo-v4 的差异裁决

### 问题

PRD 的列表 Item 字段（Chunks 数量、关键词、摘要默认收起、上传时间）与 demo-v4（仅标题 + 类型 + 按钮）不一致。demo-v4 经交互评审演进（交互评审 v0 / v1），已把关键词 + 摘要移入右区「特征」tab（由 `/docs/detail` 提供）、chunks 总数移入 ChunkRail caption，摘要收起 / 展开交互整体删除。

### 需要确认

1. 列表 Item 以 demo-v4 为准，PRD 中 Item 的「Chunks 数量 / 关键词 / 摘要」不再进入列表接口；
2. 「上传时间」按决策 2 处理；
3. 未来若 Item 需要更多字段，通过列表接口增量补充（届时讨论是否引入 chunk 数统计查询）。

### 【决定】

以 demo-v4 为准，demo-v4 为需求演进后的结果。
列表 Item 只显示标题 + 类型 + 三按钮，PRD 中的 Chunks 数量、关键词、摘要、上传时间不再进入列表接口。

## 决策 4：端点命名与路由前缀

### 问题

1. v0 命名 `/docs/list`、`/docs/detail/{id}`、`/docs/delete/{id}` 不够 REST 化（detail / delete 冗余）；
2. FastAPI 默认 swagger 文档挂在 `/docs`，与 `/docs/*` 业务路径易混淆；
3. 路由前缀现状不一致：后端现有路由无前缀（`/upload`、`/query`），但 `web/nginx.conf` 只反代 `/api/`（且 `proxy_pass http://backend:8000;` 不带 URI 重写、不剥离前缀），docker healthcheck 探的却是 `/api/health`——三处对不上，属既存 wiring 问题，新端点落位时需一并理顺；
4. demo-v4 的提示文案写的是 `/api/docs/{doc_id}/artifact?...`（暗示 `/api` 前缀）。

### 可选方案

**方案 A（推荐）**

- 端点：`GET /api/docs`（列表）、`GET /api/docs/{doc_id}`（详情）、`DELETE /api/docs/{doc_id}`（删除）；
- 前缀统一：后端路由统一挂 `/api` 前缀（FastAPI `prefix="/api"`），并修正 nginx（`proxy_pass http://backend:8000/;` 剥离前缀，或后端挂载 `/api`）与 healthcheck 路径。

**方案 B**

- 保持 v0 命名不变，仅统一前缀问题（`/api/docs/list` 等）。

**方案 C**

- 不加前缀，前端 dev 直连 8000、prod 由 nginx 反代 `/`（需改 nginx 配置，SPA fallback 与 API 分流更复杂）。

### 建议

选 **方案 A**；无论选哪个，`web/nginx.conf` 与 docker healthcheck 的前缀问题需要本次一并修复。

### 【决定】

方案 A, 存量 api 也一起加上 `/api` 前缀吧。注意在前端页面中同步修改。

## 决策 5：删除接口的幂等与部分失败语义（低优先级）

### 问题

- `doc_id` 不存在时：返回 404（语义清晰）还是 `{success: true}`（幂等）？
- 级联删除部分失败（如 Milvus 删除成功、MinIO 对象删除失败）时返回什么？是否引入异步补偿？

### 建议

- 不存在 → 404（与 detail 一致，前端弹 toast 即可）；
- 部分失败 → 记录告警日志并返回 500 或 `{success: false, detail}`，不做自动补偿（v1 阶段可接受；残留对象可在下次同名覆盖导入时被清理）。

### 【决定】

不存在 → 404，部分失败 → 记录告警日志并返回 500 或 `{success: false, detail}`，不做自动补偿。

---

## 决策 6：keywords 返回格式（低优先级）

### 问题

`后端评审v0.md` 中 detail 返回 `keywords: ["kw1", "kw2", ...]`（数组）；但 Milvus 中 `docs_keywords` 是单个逗号连接字符串，demo-v4「特征」页是前端按 `/[,，]/` 拆分。数组化需要后端定义拆分规则（关键词短语可能含逗号）。

### 可选方案

- **方案 A（推荐）**：返回入库原始字符串，前端拆分（与 demo 一致，零后端逻辑）；
- **方案 B**：后端按 `/[,，]/` 拆分返回数组（与 v0 一致，但拆分规则与入库内容强耦合）。

### 【决定】

方案 A，返回入库原始字符串，前端拆分。存量文档不考虑，需求完成后会清库处理。
