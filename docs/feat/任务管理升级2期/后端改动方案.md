## 4. 内部重要变更

### 4.1 schema：`ProgressDetail`

定义在 [task_manager.py](src/common/events/task_manager.py)（新增，紧邻 `ChildSpec`），不进 `common/schema/`（避免 tier 0 引入事件语义）。

```python
class ProgressDetail(TypedDict):
    node: str
    text: str
    metrics: dict[str, str | int | float]
```

PDF 解析中：

```json
{
  "status": "processing",
  "done_list": ["识别文档类别"],
  "running_list": ["PDF 转 Markdown"],
  "detail": {
    "node": "PDF 转 Markdown",
    "text": "24 页 · 解析中 12/24 页",
    "metrics": {
      "stage": "parsing",
      "done": 12,
      "total": 24
    }
  }
}
```

图片识别（ZIP 子任务，走 `child-progress`）：

```json
{
  "child_id": "6f1c2b9e4a7d4c1e8f3a0b5d9c2e7f41:md:0",
  "status": "processing",
  "done_list": [],
  "running_list": ["Markdown 图片识别"],
  "detail": {
    "node": "Markdown 图片识别",
    "text": "12 张图片 · 生成摘要 5/12",
    "metrics": { "stage": "vlm", "done": 5, "total": 12 }
  }
}
```

嵌入入库（向量化阶段）：

```json
{
  "status": "processing",
  "done_list": ["Markdown 图片识别", "文档切分"],
  "running_list": ["文档嵌入入库"],
  "detail": {
    "node": "文档嵌入入库",
    "text": "87 个切片 · 向量化 3/9 批",
    "metrics": { "stage": "embedding", "done": 3, "total": 9, "chunks": 87 }
  }
}
```

| 字段      | 类型   | 必填 | 说明                                                                 |
| --------- | ------ | ---- | -------------------------------------------------------------------- |
| `node`    | string | 是   | 与 `running_list` 显示名同源（`trace_node(desc=...)`），前端据此对行 |
| `text`    | string | 是   | 单行文案，≤80 字符，禁止换行 / HTML；后端生成，前端不拼语义          |
| `metrics` | object | 否   | 标量键值，≤8 键、序列化 ≤512 字节；供进度条与后续详情使用            |

`metrics` 键约定（统一 `done / total` 表达进度，前端无需按节点分支）：

| 键           | 类型   | 出现阶段            | 说明                                                                                           |
| ------------ | ------ | ------------------- | ---------------------------------------------------------------------------------------------- |
| `stage`      | string | 全部                | `uploading / queued / parsing / downloading / vlm / upload / llm / embedding / writing` |
| `done`       | int    | 有进度时            | 当前阶段完成数（页 / 张 / 批）                                                                 |
| `total`      | int    | 有进度时            | 当前阶段总数；缺省表示不确定进度                                                               |
| `chunks`     | int    | embedding / writing | 切片数                                                                                         |
| `failed`     | int    | upload              | 上传失败张数（无失败可省略）                                                                   |

约束与默认值：

- `TaskEntry.detail` 默认 `None`；快照仅在非空时输出该键，旧链路载荷保持原样。
- 不把 `doc_id`（Milvus INT64）放进 metrics / text，避免 JS 精度问题；需要时用 string 另立字段。
- 存量数据：进程内状态，无历史数据；重启后丢失与现有任务状态一致，无需迁移。

### 4.2 全局实例

| 实例 / 符号       | 定义位置                                                 | 变更                                    | 消费方                                                              |
| ----------------- | -------------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------------- |
| `TASK_MANAGER`    | [task_manager.py](src/common/events/task_manager.py:324) | 类型与生命周期不变，新增 `set_detail()` | `tracing._publish_progress`、`import_service._push_parent_progress` |
| `EVENT_BUS`       | [event_bus.py](src/common/events/event_bus.py:145)       | 不变                                    | 同上                                                                |
| `report_progress` | [tracing.py](src/common/events/tracing.py)               | 新增函数（非单例）                      | 三个节点从 `common.events.tracing` 导入                             |

`report_progress` 不从 `common.events.__init__` 导出：`tracing.py` 已 `from common.events import TASK_MANAGER`，导出会形成循环导入。节点侧既有写法就是 `from common.events.tracing import trace_node`，同模块导入即可。

实现要点：

- `_task_trace` 在调用节点前把 `(trace_id, 节点显示名)` 写入 ContextVar，`finally` 复位；`report_progress` 取上下文 → `set_detail` → `_publish_progress`。
- 无上下文（脚本直调、测试、线程池 worker）时静默 no-op，不影响节点逻辑。
- 上报失败只记 debug，不打断业务；`text` 截断、`metrics` 过滤在 `set_detail` 内完成。
- `TASK_MANAGER` 已有 `RLock`；`EVENT_BUS.push` 经 `loop.call_soon_threadsafe` 唤醒，线程安全。

### 4.3 图状态 / 节点

`ImportGraphState` 字段不变，节点链不变，三个节点的对外函数签名不变；变化只在节点内部新增上报调用。

| 节点              | 上报点                                 | 文案                                                                       |
| ----------------- | -------------------------------------- | -------------------------------------------------------------------------- |
| PDF 转 Markdown   | 上传前、每轮轮询、完成下载前           | `24 页 · 正在上传` / `排队中` / `解析中 12/24 页` / `正在下载`             |
| Markdown 图片识别 | 扫描后、每次摘要完成、每张上传完成     | `无内联图片` / `12 张图片 · 生成摘要 5/12` / `上传中 11/12 · 1 张失败`     |
| 文档嵌入入库      | LLM 前、向量化前后、写库前     | `生成关键词与摘要` / `向量化元数据` / `向量化 3/9 批` / `写入向量库`   |

实现约束：

- **线程池只做计算，上报统一回主线程**：`node_md_img.step_3` 与 `_vectorize_chunks` 都改为 `submit` + `as_completed`，在消费循环里调用 `report_progress`；worker 线程不调用（ContextVar 不会跨线程传播）。
- `_vectorize_chunks` 用 `index` 回填结果，保持「批次 ↔ 向量」一一对应，顺序语义不变。
- 图片类循环按 `max(1, total // 10)` 采样上报，并在最后一张补一帧，避免几十张图刷屏。
- 首次上报发生在扫描 / 读取完成后，因此能立刻给出总数。

`POST /api/upload` 本期无契约变化（四件套维持现状），不再重复展开。

#### `GET /api/upload/sse/{task_id}`

- 请求：路径参数 `task_id`；无 body；`Accept: text/event-stream`。
- 事件时序：`ready` → `progress` / `child-progress`（带 `detail`）→ 终态 `progress`（detail 已清理）→ `__close__`；ZIP 任务另有 `fork`。
- 响应示例（节选；为排版做了换行，实际每帧 `data:` 为单行 JSON）：

```text
event: progress
data: {"status":"processing","done_list":["识别文档类别"],"running_list":["PDF 转 Markdown"],
       "detail":{"node":"PDF 转 Markdown","text":"24 页 · 解析中 12/24 页",
                 "metrics":{"stage":"parsing","done":12,"total":24}}}

event: child-progress
data: {"child_id":"…:md:0","status":"processing","done_list":[],
       "running_list":["Markdown 图片识别"],
       "detail":{"node":"Markdown 图片识别","text":"12 张图片 · 生成摘要 5/12",
                 "metrics":{"stage":"vlm","done":5,"total":12}}}

event: progress
data: {"status":"processing","done_list":["识别文档类别","PDF 转 Markdown"],"running_list":[]}
```

- 错误：无新增状态码与错误码；通道不存在 / 已过期时沿用现状（只发 `ready` 帧、无业务事件，[sse.py](src/api/sse.py:27)）；任务失败仍走 `event: error` + `__close__`，失败信息以 `failed_list` / `error` 为准，`detail` 不承载错误。
- 调用时机：`POST /api/upload` 拿到 `task_id` 后立即连接；断线重连拿到最新快照，不依赖增量顺序。
- 重复提交：同名文件仍按新 `task_id` 独立处理（现状），各任务 `detail` 互不干扰。
- 实现落点：`report_progress` → `TASK_MANAGER.set_detail` → `_publish_progress`（[tracing.py](src/common/events/tracing.py:97)）→ `EVENT_BUS.push`。

#### `GET /api/query/sse/{session_id}`

- 仅声明兼容：查询与导入共用快照构造函数；若后续查询节点上报，`detail` 自动出现；本期查询链路无行为变化。

### 5.2 外部服务客户端

本仓没有 MinerU 封装，[node_pdf_to_md.py](src/graphs/import_graph/nodes/node_pdf_to_md.py:84) 直接 `requests` 调用。

| 调用              | 变更                                                            | 影响                                                |

VLM / Embedding / LLM 已有各自超时配置（`vlm_request_timeout` / `llm_request_timeout` 等），本期不改。

进度字段缺失（`pending` / `done` / 服务端异常）时文本回退为「排队中」或「转换完成，正在下载」，不影响导入流程。

| --------------------------- | ------------------ | -------- | ---------------------------------------------------------------------------------------------------------- |
| 进程内 `TaskManager._tasks` | `TaskEntry.detail` | 新增字段 | 随 `sweep`（30min TTL，[task_manager.py](src/common/events/task_manager.py:312)）回收，不落库、不跨 worker |

存量数据策略：**容忍**。detail 是运行时字段，无历史数据需要迁移；多 worker / 重启丢失与现有任务状态一致（`startup_checks` 已告警单 worker）。

### 5.4 前端消费契约

- 类型：`StatusResponse.detail?: { node: string; text: string; metrics?: Record<string, string | number> }`；`child-progress` 同构。
- 父任务：running 行追加 `detail.text`；折叠摘要保持原样（不加 detail）。
- 子任务：`child-progress` 同样带 `detail`；子卡片 running 行追加，摘要保持原样。
- 进度条：`metrics.done` 与 `metrics.total` 均存在且 `total > 0` 时可用；只有 `stage` 时按不确定态。
- 缺省回退：无 `detail` 时保持现有渲染，不报错、不展示空行。
- 前端不得解析中文节点名做业务判断，只按 `detail.node` 与 `running_list` 文本对齐。

兼容矩阵：

| 后端            | 前端 | 行为                       |
| --------------- | ---- | -------------------------- |
| 旧（无 detail） | 旧   | 完全不变                   |
| 旧（无 detail） | 新   | 回退旧渲染                 |
| 新（有 detail） | 旧   | 忽略未知字段，仍显示节点名 |
| 新（有 detail） | 新   | 显示阶段文案 / 进度        |

**注意**：旧前端「零改动可运行」不等于「零改动可见」；新文案必须由前端读取 `detail` 后渲染（§3.2 的 5 个文件，约 40 行）。

## 6. 关键设计决策

| 编号 | 决策点          | 结论                                                         | 理由                                                                 | 被否备选                                                                                                                   |
| ---- | --------------- | ------------------------------------------------------------ | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| D1   | 进度承载方式    | 快照新增可选 `detail`                                        | 快照幂等，断线 / 重复推送天然安全；与 P2 的 `nodes[]` 方向兼容       | 新增 `node-detail` 事件（要处理乱序 / 重连）；`nodes[]` 全量（超出本期）；复用 `child-progress`（父子语义被 md fork 占用） |
| D2   | 字段形状        | `{node, text, metrics}`，文案由后端生成                      | 前端不拼业务语义；`node` 解决 running 行归属；`metrics` 支撑进度条   | 纯字符串（前端无法定位行）；前端自行拼文案（语义分散）                                                                     |
| D3   | 推送节奏        | 阶段切换必推 + 进度变化时推（轮询 5s 一帧，图片每 10% 一帧） | 信息及时且不刷屏；同时刷新 `updated_at`，长任务不被 TTL 误清         | 每次回调都推（几十张图刷屏）；只在阶段切换推（长阶段仍静默）                                                               |
| D4   | PDF 首帧盲等    | 去掉，轮询从 t=0 开始                                        | 实测 24 页 22s 完成，原逻辑盲等 12s；100 页盲等 45s                  | 保留（进度晚出现）；分片 sleep（复杂度不值得）                                                                             |
| D5   | 请求超时        | 新增 `mineru_api_timeout` / `mineru_transfer_timeout`        | 无超时时连接卡死，`max_wait` 永远等不到                              | 硬编码（不可调）；不加（现状缺陷保留）                                                                                     |
| D6   | 终态 detail     | `add_done` / `add_failed` 按 `detail.node` 匹配清理          | 避免终态行挂过期进度，也不误清其他节点                               | 保留最后一帧（语义含糊，failed 行会误导）                                                                                  |
| D7   | PDF 进度来源    | MinerU `extract_progress`                                    | 真实页数；ETA 由早期样本反推会失真                                   | 本地估算（假进度）；只显示阶段（信息量低）                                                                                 |
| D8   | 本期范围        | 三个长节点：PDF / 图片识别 / 嵌入入库                        | 覆盖导入链路主要耗时；下载类节点信号简单但需按分支设计文案，留待后续 | 只做 PDF（图片 / 入库仍黑盒）；全节点一次接入（文案与验收面膨胀）                                                          |
| D9   | 是否给 ETA      | 不做                                                         | 页 / 张 / 批进度已足够；预估不准反而伤信任                           | 预计剩余时间（样本不足以标定）                                                                                             |
| D10  | metrics 进度键  | 统一 `done / total`（取代 v0 的 `page / total_page`）        | 前端一套进度条逻辑适配所有节点；单位由文案表达                       | 每节点自定义键（前端分支）；同时保留两套（冗余）                                                                           |
| D11  | 线程池上报      | worker 只算，主线程 `as_completed` 上报                      | ContextVar 不跨线程；主线程上报天然串行，无需锁                      | 向 worker 注入 context（易错）；worker 直接 push（拿不到节点名）                                                           |
| D12  | LLM 单次调用    | 只报阶段，不做假进度                                         | 一次 invoke 无中间信号；卡片耗时已能表达进行中                       | 按时间伪造百分比（不可信）                                                                                                 |
| D13  | 切分 / 下载节点 | 本期不做                                                     | 切分纯 CPU 秒级；下载耗时取决于外链且 zip 需按 md 分支出文案         | 一并接入（范围与验收面扩大）                                                                                               |

## 7. 风险与未决

| 风险                                   | 影响                         | 缓解                                                     |
| -------------------------------------- | ---------------------------- | -------------------------------------------------------- |
| `extract_progress` 只在 `running` 返回 | 排队阶段没有页数             | `pending` 回退「排队中」，其余无页数回退「解析中」，只展示阶段 |
| 页数跳变（实测 1→7→12）甚至回退        | 进度条倒退                   | 节点侧单调钳制：`done = max(上次 done, extracted_pages)` |
| 线程池 contextvals 丢失                | 上报静默失效                 | 所有上报回主线程；worker 不调用（D11）                   |
| `as_completed` 打乱批次顺序            | 向量与切片错位               | submit 时携带 index，结果回填后按原顺序组装              |
| 图片上传失败被跳过                     | done 数虚高                  | 单独记 `failed`，文案显示「N 张失败」                    |
| 几十张图高频上报                       | SSE 帧过多                   | 每 10% + 最后一张采样；单节点 ≤12 帧                     |
| 事件量：600 页 PDF                     | 约 1206 帧，占 2000 缓冲 60% | 当前上限内；后续可降为每 2 轮一帧                        |
| LLM 阶段无中间信号                     | 30–90s 只有一条文案          | 展示阶段文案 + 卡片耗时；不做假进度（D12）               |
| 单 worker 进程内状态                   | 多 worker 下 detail 不一致   | 与现状一致；`startup_checks` 已告警                      |
| 请求超时与 `max_wait` 叠加             | 实际停止略超上限             | 按「max_wait + 单次请求超时」描述，不承诺精确截止        |

假设（PRD / 代码未写明、按现有模式补，被推翻则改方案）：

1. MinerU 批量接口在 `state=running` 时稳定返回 `extract_progress`（当前 1 次实测）。
2. 导入任务始终单文件、单 batch，`extract_result[0]` 即本任务结果。
3. 前端可接受 `progress` / `child-progress` 上的新增可选字段。
4. 单个任务内父图节点串行；ZIP 子任务并行但各有独立 `TaskEntry`，互不覆盖。
5. 图片每 10%、向量化每批的采样频率足以表达进度。

⏳ 未决：

1. ✅ 前端 5 个文件已随本期接入（types ×2 / store / 父卡片 / 子卡片），联调通过。
2. 在线图片下载与文档切分是否下一期接入 —— 需要人类定优先级；不阻塞本期三节点。
